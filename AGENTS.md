# Agent Guide: MiCAR Whitepaper Linter

Welcome, AI Agent! This guide details conventions, directory mapping, and rules safety for the `micar-whitepaper-linter` workspace.

---

## 1. Project Purpose
The MiCAR Whitepaper Linter is a deterministic Python package that screens draft crypto-asset white papers under the Markets in Crypto-Assets Regulation (MiCAR - Regulation (EU) 2023/1114). It flags candidate disclosure gaps against Annexes I, II and III and the common requirements of Articles 6, 19 and 51, each with a citation. It is first-pass tooling for lawyer review: it does not decide whether a white paper is compliant. The text report, the CI outputs and the playground say it is not legal advice; the `--json` report, the Markdown audit log, the `--coverage` table and the remediation JSON carry no such notice. It runs as a CLI (`micar-lint`), as a GitHub Action (`action.yml`) and in a browser playground (`docs/playground/`, on Pyodide).

## 2. Directory Layout
- `src/micar_linter/`: Core source package.
  - `rules/`: Rule definitions. `annex_i.py`, `annex_ii.py` and `annex_iii.py` hold the Annex I, II and III rules. `common.py` holds the rules every white paper type runs (summary, risk warning, management statement, notification date, language, the iXBRL format gate and the LEI checks). `base.py` defines `Severity`, `Rule` and `Finding`. `__init__.py` builds `RULESETS`: the common rules plus Annex I for `other`, Annex II for `art` and Annex III for `emt`.
  - `linter.py`: `Linter`, `Report` and `lint_whitepaper`, plus the logic of the rules that are not generic checks.
  - `whitepaper.py`: the `Whitepaper` input model, the `WhitepaperType` regimes and `load_whitepaper`, which dispatches by file suffix.
  - `document.py`: PDF, DOCX and Markdown section extraction for `load_whitepaper`, and `match_heading_to_section` (`SECTION_PATTERNS`), the heading-to-section matching every heading-based path uses: these loaders, `xhtml_parser.py`, `document_loader.py`, and the finding locations in `anchors.py` and `locations.py`. JSON drafts do not use it. Numbered-field XHTML does not use it for section extraction or in `locations.py`, which skips headings for that layout, but `anchors.py` matches the id-bearing h1 to h6 headings of every XHTML source, numbered-field drafts included (for a saved iXBRL viewer page it parses the page itself, which has none). `document_loader.py` is a separate loader for the Title II study batch (`micar-lint-batch`) with its own PDF, XHTML and text extraction; it splits PDF and text into sections with `sections_from_lines` from `document.py`, the heading-shape rule of `micar-lint` without font information, so a change to that rule changes the study batch too. `anchors.py` and `locations.py` re-parse XHTML headings themselves (h1 to h6 only, without the bold-run headings `xhtml_parser.py` also detects). Separately, the JSON line lookup in `locations.py` mirrors `sectionSelection` in `docs/playground/model.mjs`; that mirror covers JSON section keys only. `parseDraft` in the same file validates JSON drafts more strictly than the CLI (a string `type` is required, at most 1 MB), so a change to the accepted JSON input needs it and `tests/playground/model.test.mjs` updated too. A heading-parsing change may therefore be needed in several places.
  - `xhtml_parser.py`: XHTML text extraction and heading-based section mapping. `numbered_fields.py` handles white papers in the numbered-field layout of Implementing Regulation (EU) 2024/2984. `xhtml_parser.py` also reads saved iXBRL viewer pages: `is_script_packed` spots a page with next to no visible text and a script over 10,000 characters, and `unpack_script_payload` decodes the base64 such a page carries (as a quoted string, a `data:` URI, a JSON-escaped string or a script holding only base64; gzip, zlib, raw deflate or uncompressed markup; a page that packs more than one distinct document is refused), inflating at most `MAX_UNPACKED_BYTES` (8 MB, equal to `MAX_XHTML_BYTES` in `docs/playground/model.mjs`, which `tests/test_viewer_page.py` checks). Both parse the page with `huge_tree`, because libxml2 otherwise drops a text node above about 10 million characters. `whitepaper.py` passes the unpacked bytes to `extract_numbered_fields` and `load_from_xhtml`, which take a path or bytes, so no temporary file holds draft text, and puts `VIEWER_PAGE_NOTE` first in the extraction notes (with `VIEWER_EMPTY_NOTE` when no section was read). For every numbered-field draft, viewer page or not, `sections_from_numbered_fields` adds `MERGED_LABELS_NOTE` when `labels_run_into_answers` finds that four in five lettered fields have no separate label, as in a rendering converted from PDF or a table that sets the label in the answer cell: an "N/A" answer can then read as answered, and the note asks for each Pass to be checked. `source_file` stays the viewer page, so `anchors.py` and `locations.py` find no headings in it and fall back to hash anchors and line 1.
  - `ixbrl.py`: Inline XBRL format checks (the iXBRL 1.1 namespace and facts tagged with the ESMA MiCA taxonomy). It does not check tag completeness.
  - `lei.py`: LEI format, check digits and party sections, used by the two LEI rules.
  - `placeholders.py`: `is_placeholder` ("TBD", "TBC", "[●]", "noch offen") and `is_not_applicable` ("N/A", "none", a dash). On the generic checks in `linter.py`, a section holding only placeholders is missing; "N/A" is a short answer under review. `numbered_fields.py` marks an "N/A" field unanswered: it adds "N/A" without the field label, warns when a whole part is "N/A", and leaves "N/A" out of a part whose other fields hold only placeholders, so that part is missing. `document.py` uses both only in heading detection.
  - `esma_register.py`, `study_report.py` and `review_validation.py` serve the study only (section 6). `esma_register.py` fetches the ESMA register over the network; keep it out of the checking path.
  - `report.py`: Renders a `Report` as text, JSON, a Markdown audit log or a coverage table. Its `render_extraction_notes` gives the audit log, `review-table.md` and `reviewer-signoff.md` the same Extraction Notes section. `markdown_line` puts each warning, the draft title and the audit log's source path on one line with Markdown escaped, because a JSON title, a file name or a section key quoted in an unrecognised-section warning can carry line breaks and Markdown; those section keys are also why the CI outputs leave the warnings out. Pass any new value from the draft or its file name in these files through it. Other outputs have their own modules, among them `ci_outputs.py` (SARIF, job summary, annotations), `review_table.py`, `review_bundle.py`, `remediation.py`, `coverage.py`, `artifact_manifest.py`, `batch.py`, `workspace.py` and `collaboration_workspace.py`.
- `tests/`: Pytest tests (`test_*.py`) and Node tests for the playground (`tests/playground/*.test.mjs`). Pytest does not run the Node tests; `make playground-check` does.
- `examples/`: Synthetic inputs with fictional issuers (JSON, XHTML, DOCX). They contain no real issuer data.
  - `art-stablecoin.json`, `emt-token.json` and `other-crypto-asset.json` are full drafts with fictional `SYNTH` LEIs. Each still has open blockers, the iXBRL format gate among them, so `--strict` exits 1.
  - `incomplete.json` is deliberately incomplete.
  - `numbered-other-draft.xhtml` uses the numbered-field layout and needs `--type other`.
  - `review-bundle/` is a committed sample output (see section 6).
- `docs/`: The GitHub Pages root: landing page, `playground/`, generated `rules/`, `adr/` (architecture decisions) and `research/`. `docs/playground/lint.py` is the browser bridge; it is not in the wheel. `make lint` runs ruff on `src`, `tests` and `scripts` only, so `docs/playground/lint.py` and the study's own `scripts/` are not linted.
- `studies/`: The Title II white paper study. Its committed files hold public ESMA register metadata (real issuer names and URLs) and short matched-text excerpts; raw white papers are never committed (they stay in the git-ignored `.study-cache/`). `research/_captures/` is git-ignored third-party material that stays local; `research/screenshots/` holds committed screenshots of this repo's own playground.
- `scripts/`: Generators and checks, plus `export-whitepaper-starter.sh` (`make template-export`), which deletes and recreates the local branch `release/micar-whitepaper-template`. `templates/whitepaper-starter/`: source of the starter template. `action.yml`: the GitHub Action.

## 3. Important Development Commands
Ensure you run commands using `uv` or inside your virtual environment. `make check` needs Python 3.13 or later and Node.js 22 or later.
- `make check`: Run ruff, pytest, the CLI smoke run and the review-bundle build (through `uv run --extra dev`), then the playground checks (`node --check`, `node --test`) and the starter-template check (with the system `python3`).
- `uv run micar-lint <file>`: Run linter against a document. XHTML in the numbered-field layout needs `--type other|art|emt`; `--type` and `--lang` apply only to a single-file run. `--compare-review-table-output` and the workspace, workflow and collaboration-bundle modes therefore stop on numbered-field XHTML with exit 2, while the directory batch (`--batch-output`) skips such a file with a `lint-failed:` warning and counts it in `failed_files`; `--strict` exits 1 on a failed file and on a run that linted no file. A JSON draft keeps its own `type`, and `--type` is ignored for it without a warning. A single-file run that cannot load its input (a missing file, invalid JSON, numbered-field XHTML without `--type`, a viewer page that cannot be unpacked or unpacks to more than 8 MB) exits 1 with a message, the same code `--strict` uses for open blockers. DOCX needs the `docx` extra, e.g. `uv run --extra docx micar-lint draft.docx`. `--coverage` (without `--review-bundle-dir`) prints its table instead of the report; output files and `--strict` still apply.
- `make dist`: Build the wheel and the sdist into `dist/` from `git archive HEAD`, so uncommitted changes and untracked files stay out. It deletes `dist/` first, including the `make review-bundle` output there.
- `uv run --extra dev pytest`: Run test suite with dev tooling available.
- `uv run --extra dev ruff check src tests scripts`: Lint code with dev tooling available.

## 4. Coding Conventions
- **Regulatory Rules**: centralize all rules in [src/micar_linter/rules/](src/micar_linter/rules/). Each rule is an instance of the frozen `Rule` dataclass in `rules/base.py`; there is no `BaseRule` class to inherit from. `Linter` in `linter.py` applies the generic checks (a section that is empty or holds only placeholder text is missing; then listed terms, required and prohibited patterns, minimum words, with German variants for German drafts), and dispatches by rule ID the rules that need their own logic. The one exception to `rules/` is the batch study: `batch.py` defines a separate `StudyRule` set (`STUDY_RULES`, IDs such as `ANNEX_I_PART_A_02_LEGAL_FORM`) used only by `micar-lint-batch`, outside `RULESETS` and without rule pages.
- **Rules with their own logic**: besides the dispatch in `linter.py`, handle the rule ID everywhere `scripts/build_rule_docs.py` special-cases rules: the sets `FORMAT_GATE`, `LEI_RULES` and `NEVER_PASS` where they apply, a branch in `examples()`, a branch in `status_logic()` and the limitations in `rule_page()` (a new rule family needs an entry in `SOURCE_MODULES`, or the build fails; an entry in the optional `UNTESTED_REGIMES` adds a public "not yet run against a real white paper" note to its pages, which "Known limits" in `docs/index.html` repeats by hand, as it does "Point-level checks are not built yet"). Its examples must include a `missing` and a `pass` case unless the rule is in `NEVER_PASS` (`tests/test_rule_docs.py`). A format-gate rule also goes in `FORMAT_GATE_RULES` in `ci_outputs.py`, which keeps it out of the annotations and the summary table, and in the `COMMON.IXBRL_TAGGING` check in `docs/playground/app.mjs` that hides "Inspect section"; the job summary's "Format gate" note in `ci_outputs.py` and the playground explainer in `docs/playground/index.html` are worded for iXBRL and need rewording for another gate. If its issue messages can quote draft text, add it to `DRAFT_ECHO_RULES` in `ci_outputs.py` and to the hand-written copies of that list in `docs/API.md` (CI outputs) and ADR 0001, so SARIF result messages use a fixed sentence instead (the job summary and annotations never print issue messages).
- **Generic rules without listed terms**: the rule-page generator builds its passing example from `required_terms` and `min_words` only. A generic rule that relies on `required_patterns`, or has no terms and `min_words=0`, needs its own branch in `examples()` in `scripts/build_rule_docs.py`, or the page build stops.
- **New section keys**: a rule that reads a new section key also needs a heading pattern in `SECTION_PATTERNS` (`document.py`), which the PDF, DOCX, Markdown and heading-based XHTML/HTML loaders use. For numbered-field XHTML it needs a mapping in `numbered_fields.py` for each regime it applies to: `_PART_SECTIONS` for a lettered part, or `_SUMMARY_SECTIONS` for a leading field (as `summary`, `risk_warning`, `management_statement` and `notification_date` are; `language` is found by its field label). Without them those loaders never fill the key, so a rule on the generic checks always reports missing for those drafts.
- **Playground dependencies**: the playground installs the wheel with `deps=False` (`docs/playground/runtime.mjs`) and loads lxml only on the first XHTML check; pypdf and python-docx are never available there. The modules `docs/playground/lint.py` reaches on the JSON path (the package `__init__.py`, `linter`, `report`, `whitepaper`, `anchors`, `lei`, `document`, `placeholders`, `citations`, `rules/`) must not import lxml, pypdf, python-docx or a new third-party package at module level, directly or by importing `ixbrl.py`, `xhtml_parser.py`, `numbered_fields.py` or `collaboration_workspace.py` (which import lxml at the top) or `cli.py` (which imports `collaboration_workspace.py`). No automated check runs Pyodide, and the pytest suite has every dependency installed, so a break here goes unnoticed.
- **Promised constraints**: no language model and no network call in the CLI checking path; the CLI runs locally (`PRIVACY.md`, `docs/SETUP.md`) and the LEI rules query no registry (ADR 0007). The playground sends no draft text off the page: it fetches only the Pyodide runtime, its packages (lxml on the first XHTML check) and its own static files, and it keeps no browser storage, cookies or telemetry (`docs/SETUP.md`, `docs/index.html`, ADR 0006). The SARIF log, job summary and annotations carry no draft text and no timestamps, so they are byte-reproducible (`ci_outputs.py`, ADR 0001); the job log still prints the full text report.
- **Pinned dependencies**: every `uses:` in `action.yml` and `.github/workflows/ci.yml` is pinned by commit SHA (ADR 0001 records the `action.yml` pins); keep new Action dependencies pinned the same way.
- **Draft-supplied metadata**: every top-level JSON key other than `title`, `type` and `sections` becomes `Whitepaper.metadata`, which rule logic reads. Only the keys in `_RESERVED_METADATA_KEYS` (`whitepaper.py`) are stripped, and the JSON loader forces `ixbrl_validated` to false. A new trust or validation flag must be added there, or a draft can certify itself (see the self-certification test in `tests/test_playground_bridge.py`). `source_file` is reserved and set only by the document loaders: `anchors.py` takes the source type from it and parses the file it names, and `_ixbrl_finding` picks its message from it. `script_packed_source` is reserved too and set only by the XHTML loader, for a saved iXBRL viewer page.
- **Fail Closed**: Compliance checks must fail closed on missing sections. `ANNEX_II.G.DEPOSIT_FLOOR_REVIEW` never returns pass (`_deposit_floor_finding` has no pass branch). `COMMON.IXBRL_TAGGING` never passes for any loaded draft: JSON, the other draft formats and saved iXBRL viewer pages give missing (for a viewer page `validate_ixbrl` does not run, and `script_packed_source` selects the message), and other XHTML stays at review because `validate_ixbrl` never returns an empty issue list (when the namespace checks pass it still adds the tag-completeness note). `_ixbrl_finding` itself has a pass branch for an empty list, so a change to `ixbrl.py` must keep at least one issue or the gate opens.
- **Citations**: `Rule.citation` uses the canonical German form (e.g. `Art. 6 Abs. 7 MiCAR`). A newly cited act needs an entry in `ACT_URLS` in `citations.py` and, unless it is a `VO (EU)` regulation or its name is already English (as `MiCAR` is), an English name mapping in `to_english()`. For every rule citation, `tests/test_citations.py` checks that no listed German drafting term or doubled comma survives the conversion, that the numbers survive, and that at least one EUR-Lex link results (MiCAR's when MiCAR is cited); `test_known_conversions` pins the exact output of five fixed citations. It does not catch a second act missing from `ACT_URLS` or an untranslated act name, so check `source_urls()` and `to_english()` for the new citation, or add a `test_known_conversions` case.
- **Stable rule IDs**: rule IDs are stable identifiers (`rules/base.py`): add new rule IDs, never rename existing ones. They key SARIF results, the rule-page URLs and review bundles.
- **Report language is load-bearing** (CONTRIBUTING.md): the blocker, lawyer sign-off and audit-log wording is pinned in `tests/test_report.py`. Never describe a pass as compliance.
- **Synthetic data only**: CONTRIBUTING.md requires fictional fixtures in `examples/`; keep tests, playground samples and the starter template the same way. Add no real white paper text, issuer or token names, IBANs or wallet addresses there (issuers and tokens in the examples are fictional, but they name the Ethereum network, the authorities BaFin, EBA and ESMA, and real places such as German cities; `sample-draft.docx` does not label its issuer as fictional). Real register data lives only in the study under `studies/` (see section 2); `docs/research/` names real vendors and products as market research.
- **Owner-reserved work**: `TODO(human)` marks code reserved for the owner, such as `displayCitation` in `docs/playground/model.mjs`. Leave it, and leave the items under "Needs owner decision" in `docs/research/adaptation-plan.md` to the owner.
- **README.md** is the PyPI description, so `tests/test_readme.py` caps it at 350 words, allows no relative links, checks that every `https://github.com/sebastianfoerste/micar-whitepaper-linter/blob/main/` link resolves to a local file and heading, and requires links in that form to `docs/SETUP.md#quick-start`, `docs/DETAILS.md` and `docs/overview.md`. It also checks every relative link and anchor in `docs/SETUP.md`, `docs/DETAILS.md`, `docs/overview.md` and `docs/TESTING.md`, so renaming a heading there can fail it. Link repository files in that form, and put longer content in those docs.
- **Changelog and flags**: record user-facing changes under "Unreleased" in `CHANGELOG.md`, and document every new `cli.py` flag in `docs/API.md` (no test enforces either).
- **Older docs**: `docs/ARCHITECTURE.md` still says rules inherit from `BaseRule`, and it and `docs/FEATURES.md` use compliance wording ("compliant parameters", "regulatory rejection"). `docs/rule-extension-guide.md`, `docs/SETUP.md` and CONTRIBUTING.md describe the rule steps and output paths more narrowly than this file, `templates/whitepaper-starter/README.md` says custody is always staged for human review although `ANNEX_II.G.CUSTODY` can pass, `docs/launch-readiness.md` calls `art-stablecoin.json` "the passing ART example" although it has open blockers, `docs/COLLABORATION_PROGRAMME.md` says `SOURCE_DATE_EPOCH` makes workspace and bundle outputs byte-identical although only `review_table.py` and `collaboration_workspace.py` read it and the workspace vault and the review bundle stamp the current time, and `docs/WHITEPAPER_STARTER_RELEASE.md` mentions a `template-release` remote with a disabled push URL that a fresh checkout does not have (only `origin` exists). Where they disagree with this file or the code, the code wins. Some shipped output names also say "compliance" (the audit log title, `compliance-checklist.md` in the review bundle); they are fixed file and section names, not verdicts.

## 5. Files to Protect
Do not casually modify:
- `src/micar_linter/rules/base.py`: Core rule data types (`Severity`, the frozen `Rule` dataclass, `Finding`) that the whole package imports.
- `pyproject.toml` and `uv.lock`: Build and lock configs. CI installs with `uv sync --locked`.

## 6. Generated and Committed Outputs
Generated files must not be edited by hand; regenerate them after the change that affects them. Hand-maintained copies listed here must be updated by hand at the same time:
- `docs/rules/*.html`: run `uv run python scripts/build_rule_docs.py` after any change to rules, `citations.py`, `lei.py`, the script itself or the version; the pages embed rule fields, converted citations and generated LEIs. Each example's stated status and the status-logic and limitation text are written by hand in the script. The build stops if an example's linted status differs, but a changed check whose examples still give the same status leaves the hand-written text stale, so update the script when you change rule logic in `linter.py` or placeholder detection in `placeholders.py`. `lint_example` in the script builds each example's `Whitepaper` with a copy of the JSON loader's metadata filter, so a new default in `_load_json` needs copying there. `tests/test_rule_docs.py` fails on stale pages and lints every example on them.
- `docs/playground/micar_whitepaper_linter-<version>-py3-none-any.whl`: after any change under `src/`, delete the wheel and run `uv build --wheel -o docs/playground/`. `tests/test_playground_wheel.py` checks that it matches the source, the project version and `docs/playground/index.html`. That `uv build` command also writes an untracked `docs/playground/.gitignore` containing `*`, which hides new files in that folder from `git status`; use `git add -f` for a wheel with a new name.
- `docs/playground/samples.json` and `docs/playground/sample-numbered.xhtml`: run `make playground-samples` after editing the examples they are built from or `SAMPLES` in `scripts/build_playground_samples.py`; pytest (`test_bundled_samples_match_canonical_examples` in `tests/test_playground_bridge.py`) fails while they are stale. `tests/playground/model.test.mjs` expects exactly four entries in `samples.json`, so a fifth sample, once regenerated, fails the Node tests (`make playground-check`). A new sample needs an `<option>` in the `#example` select in `docs/playground/index.html` to be selectable; also add its key to the list in `loadSamples` in `docs/playground/app.mjs`, which checks each listed sample with `parseDraft` when the page loads (an unlisted key still loads, unchecked).
- Sample CLI output: `make sample-reports` writes `reports/sample-art-pass.txt` and `reports/sample-incomplete-blockers.txt` (the text reports for `art-stablecoin.json` and `incomplete.json`) and the CLI output block of `docs/sample-review-bundle.md`; `make demo-image` writes `docs/demo.png` and `docs/demo.txt` from `incomplete.json` and needs Chrome (see `scripts/render_demo.py`). Without Chrome, a change to that report leaves `make check` red: say the demo files are stale rather than hand-editing them, since the test also checks the PNG's size and stamp. `tests/test_sample_reports.py` and `tests/test_demo_capture.py` fail while these are stale. The output blocks in `README.md` and `docs/DETAILS.md` are edited by hand; `tests/test_readme.py` checks they are the first lines of the real output. `examples/review-bundle/` is a copy of the `make review-bundle` output for `art-stablecoin.json` (that target writes to the git-ignored `dist/review-bundle/`), refreshed by hand, as is everything in `docs/sample-review-bundle.md` except its CLI block; the bundle stamps the current time, so a refresh changes `generated_at` and the digests even when nothing else changed. Despite its name, `reports/sample-art-pass.txt` shows open blockers. `tests/test_reserve_rules.py` reads `review-table.json` and `sample-art-pass.txt`, but no test compares the bundle with fresh output. A change to rules or report wording can make any of them stale, and a change to bundle wording the bundle files. `examples/art-stablecoin.json` feeds `sample-art-pass.txt`, `examples/review-bundle/` and `docs/sample-review-bundle.md`; `examples/incomplete.json` feeds `sample-incomplete-blockers.txt`, `docs/demo.png`, `docs/demo.txt` and the README and DETAILS blocks. Refresh them together.
- `studies/2026-07-title-ii-annex-i-whitepaper-study/` (commands in its README):
  - Do not run the README's commands or the study's `scripts/` as written. The first README command runs `esma_register` into `source-manifest.json` (see the next point). `micar-lint-batch`, which `scripts/run_batch.py` also runs, excludes every document as `cached_document_not_found` without `.study-cache/`, still overwrites `findings-pseudonymous.json` and `.csv` with that result, and exits 0; `scripts/render_report.py` overwrites `findings-summary.md`. Write to a scratch path instead.
  - Do not regenerate the study inputs. `source-manifest.json` and `document-provenance.json` are curated: `python -m micar_linter.esma_register` cannot reproduce the manifest (it drops entries and provenance fields), and the study's scripts overwrite `source-manifest.json` and `sample-manifest.csv`: `scripts/fetch_esma_register.py` from the live ESMA register CSV, and `scripts/select_sample.py` from a local CSV, by default `sample-manifest.csv` itself.
  - `micar-lint-batch` writes `findings-pseudonymous.json` and `.csv` from the manifest and the git-ignored `.study-cache/` (absent in a fresh checkout). A change to the study detector in `batch.py` or to `document_loader.py`, `document.py` or `placeholders.py` leaves them stale until the study is re-run with its cache. The committed findings (generated 2026-07-06) predate later changes to `document_loader.py`, `document.py` and `batch.py` (8e76d8d, 0ee2db7, a0150b8) and the new `placeholders.py`, so a re-run may already differ.
  - `micar-study-report` renders `findings-summary.md` from the committed JSON alone (no cache needed), so re-render it after changing `study_report.py`. The committed summary predates the current `study_report.py` wording, so a re-render changes it even without new findings.
  - `micar-review-summary` writes `human-review-summary.json` from `human-review-matrix.csv`; a re-run changes its `completion_rate` from `0` to `0.0`. The `human-review-*.csv` files are worksheets for human reviewers under `review-protocol.md`; never fill them in yourself.
  - Do not hand-edit these outputs. `tests/playground/model.test.mjs` checks the study figures in `docs/playground/index.html` against `findings-pseudonymous.json` and `human-review-summary.json`; the figures in `docs/overview.md`, `docs/DETAILS.md` and the study README's "Current status" are not checked by any test.
- `contracts/micar-whitepaper-linter.proof.v1.json` is a hand-maintained interface contract (entry points, `action.yml`, `make check`); nothing reads or tests it, so update it when those interfaces change. The contract is already behind: its `interfaces` name two of the five console scripts in `pyproject.toml` (`micar-lint` and `micar-lint-batch`, besides `action.yml`), and its `contractTest`, `tests/test_review_validation.py`, does not read it. The `action.yml` inputs are also described by hand in `docs/DETAILS.md` (inputs table) and `docs/SETUP.md` (usage).
- The version appears in `pyproject.toml`, `uv.lock` (run `uv lock`, or CI's `uv sync --locked` fails), `src/micar_linter/__init__.py`, `CITATION.cff` (with `date-released`), the playground wheel's filename, `docs/playground/index.html` and every page in `docs/rules/` (regenerate them). Work listed under "Unreleased" in `CHANGELOG.md` keeps the last release's number until the owner releases, so the rule pages and the wheel show it for unreleased code.

## 7. Git and Branching Rules
Do not merge feature branches into `main`, `master` or `develop`, and do not push to those remote branches, unless the user approved it in the current session or the change goes up as a pull request for review. These branches deploy; an unreviewed merge cannot be recalled.

Before proposing a merge or push, run `make check` on the feature branch. It runs ruff, the pytest suite (which asserts several of the `*.v1` output schema identifiers), the CLI smoke run, the review bundle, the playground checks and the starter-template contract. CI runs only on pushes and pull requests to `main`, so on a feature branch `make check` is the only gate. The project has no database, so there are no migrations to validate.

Up to 1.1.1 the GitHub Action was released through its own tags (`v1.0.0`, `v1.1.0`, `v1.1.1`), separate from the package version tags (`v0.1.0` to `v0.2.1`). From 1.2.0 the package and the Action share one version number: one tag such as `v1.2.0` marks the PyPI release and the Action release, and `v1` moves to it (`CHANGELOG.md` lists the earlier releases of both lines). Users and the starter template pin `@v1`, so moving `v1` changes the Action for every user; only the owner creates release tags or moves `v1`. Release files for PyPI come from `make dist`: hatchling puts every file that `.gitignore` does not exclude into the sdist, so a plain `uv build` in a working tree also packs untracked files, which is how the 1.2.0 sdist on PyPI came to contain local `.claude/worktrees/` copies. `scripts/check_whitepaper_starter.py` (`make template-check`) requires the starter workflow file to keep containing the strings `uses: sebastianfoerste/micar-whitepaper-linter@v1`, `whitepaper: whitepaper.json` and `strict: 'false'` (a substring check). `action.yml` runs `uvx` with the `docx` extra, and `--coverage` keeps the strict gate and the CI outputs. The `action` job in `.github/workflows/ci.yml` runs `action.yml` from the checkout: strict on `examples/incomplete.json`, which must fail, and in report mode on `examples/sample-draft.docx` with `--type other`; both runs must write a SARIF log. Until `v1` is moved to `v1.2.0`, `@v1` runs `v1.1.1` (package 0.2.0), which predates both and much more: it has no CI outputs, LEI rules, placeholder detection, numbered-field support or `--type` flag, and pins `setup-uv` by tag. The docs describe the Action as of 1.2.0 and mark the inputs that need it, so `v1` should move when the release is merged.
