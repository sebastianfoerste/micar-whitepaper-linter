# Agent Guide: MiCAR Whitepaper Linter

Welcome, AI Agent! This guide details conventions, directory mapping, and rules safety for the `micar-whitepaper-linter` workspace.

---

## 1. Project Purpose
The MiCAR Whitepaper Linter is a deterministic Python package that screens draft crypto-asset white papers under the Markets in Crypto-Assets Regulation (MiCAR - Regulation (EU) 2023/1114). It flags candidate disclosure gaps against Annexes I, II and III and the common requirements of Articles 6, 19 and 51, each with a citation. It is first-pass tooling for lawyer review: it does not decide whether a white paper is compliant. The text report, the CI outputs and the playground say it is not legal advice; the `--json` report, the Markdown audit log, the `--coverage` table and the remediation JSON carry no such notice. It runs as a CLI (`micar-lint`), as a GitHub Action (`action.yml`) and in a browser playground (`docs/playground/`, on Pyodide).

---

## 2. Directory Layout
- `src/micar_linter/`: Core source package.
  - `rules/`: Rule definitions. `annex_i.py`, `annex_ii.py` and `annex_iii.py` hold the Annex I, II and III rules. `common.py` holds the rules every white paper type runs (summary, risk warning, management statement, notification date, language, the iXBRL format gate and the LEI checks). `base.py` defines `Severity`, `Rule` and `Finding`. `__init__.py` builds `RULESETS`: the common rules plus Annex I for `other`, Annex II for `art` and Annex III for `emt`.
  - `linter.py`: `Linter`, `Report` and `lint_whitepaper`, plus the logic of the rules that are not generic checks.
  - `whitepaper.py`: the `Whitepaper` input model, the `WhitepaperType` regimes and `load_whitepaper`, which dispatches by file suffix.
  - `document.py`: PDF, DOCX and Markdown section extraction for `load_whitepaper`, and `match_heading_to_section` (`SECTION_PATTERNS`), the heading-to-section matching every heading-based path uses: these loaders, `xhtml_parser.py`, `document_loader.py`, and the finding locations in `anchors.py` and `locations.py`. JSON drafts do not use it. Numbered-field XHTML does not use it for section extraction or in `locations.py`, which skips headings for that layout, but `anchors.py` matches the id-bearing h1 to h6 headings of every XHTML source, numbered-field drafts included. `document_loader.py` is a separate loader for the Title II study batch (`micar-lint-batch`) with its own PDF, XHTML and text extraction. `anchors.py` and `locations.py` re-parse XHTML headings themselves (h1 to h6 only, without the bold-run headings `xhtml_parser.py` also detects). Separately, the JSON line lookup in `locations.py` mirrors `sectionSelection` in `docs/playground/model.mjs`; that mirror covers JSON section keys only. A heading-parsing change may therefore be needed in several places.
  - `xhtml_parser.py`: XHTML text extraction and heading-based section mapping. `numbered_fields.py` handles white papers in the numbered-field layout of Implementing Regulation (EU) 2024/2984.
  - `ixbrl.py`: Inline XBRL format checks (the iXBRL 1.1 namespace and facts tagged with the ESMA MiCA taxonomy). It does not check tag completeness.
  - `lei.py`: LEI format, check digits and party sections, used by the two LEI rules.
  - `report.py`: Renders a `Report` as text, JSON, a Markdown audit log or a coverage table. Other outputs have their own modules, among them `ci_outputs.py` (SARIF, job summary, annotations), `review_table.py`, `review_bundle.py`, `remediation.py`, `coverage.py`, `artifact_manifest.py`, `batch.py`, `workspace.py` and `collaboration_workspace.py`.
- `tests/`: Pytest tests (`test_*.py`) and Node tests for the playground (`tests/playground/*.test.mjs`). Pytest does not run the Node tests; `make playground-check` does.
- `examples/`: Synthetic inputs with fictional issuers (JSON, XHTML, DOCX). They contain no real issuer data.
  - `art-stablecoin.json`, `emt-token.json` and `other-crypto-asset.json` are full drafts with fictional `SYNTH` LEIs. Each still has open blockers, the iXBRL format gate among them, so `--strict` exits 1.
  - `incomplete.json` is deliberately incomplete.
  - `numbered-other-draft.xhtml` uses the numbered-field layout and needs `--type other`.
  - `review-bundle/` is a committed sample output (see section 6).
- `docs/`: The GitHub Pages root: landing page, `playground/`, generated `rules/`, `adr/` (architecture decisions) and `research/`. `docs/playground/lint.py` is the browser bridge; it is not in the wheel and ruff does not lint it.
- `studies/`: The Title II white paper study. Its committed files hold public ESMA register metadata (real issuer names and URLs) and short matched-text excerpts; raw white papers are never committed (they stay in the git-ignored `.study-cache/`). `research/_captures/` is git-ignored third-party material that stays local; `research/screenshots/` holds committed screenshots of this repo's own playground.
- `scripts/`: Generators and checks, plus `export-whitepaper-starter.sh` (`make template-export`), which deletes and recreates the local branch `release/micar-whitepaper-template`. `templates/whitepaper-starter/`: source of the starter template. `action.yml`: the GitHub Action.

## 3. Important Development Commands
Ensure you run commands using `uv` or inside your virtual environment. `make check` needs Python 3.13 or later and Node.js 22 or later.
- `make check`: Run ruff, pytest, the CLI smoke run and the review-bundle build (through `uv run --extra dev`), then the playground checks (`node --check`, `node --test`) and the starter-template check (with the system `python3`).
- `uv run micar-lint <file>`: Run linter against a document. XHTML in the numbered-field layout needs `--type other|art|emt`. DOCX needs the `docx` extra, e.g. `uv run --extra docx micar-lint draft.docx`. `--coverage` (without `--review-bundle-dir`) prints its table and exits 0 before `--strict` is applied and before any output file (SARIF, summary, annotations, audit log, remediation, manifest) is written.
- `uv run --extra dev pytest`: Run test suite with dev tooling available.
- `uv run --extra dev ruff check src tests`: Lint code with dev tooling available.

## 4. Coding Conventions
- **Regulatory Rules**: centralize all rules in [src/micar_linter/rules/](src/micar_linter/rules/). Each rule is an instance of the frozen `Rule` dataclass in `rules/base.py`; there is no `BaseRule` class to inherit from. `Linter` in `linter.py` applies the generic checks (listed terms, required and prohibited patterns, minimum words, with German variants for German drafts), and dispatches by rule ID the rules that need their own logic. The one exception to `rules/` is the batch study: `batch.py` defines a separate `StudyRule` set (`STUDY_RULES`, IDs such as `ANNEX_I_PART_A_02_LEGAL_FORM`) used only by `micar-lint-batch`, outside `RULESETS` and without rule pages.
- **Rules with their own logic**: besides the dispatch in `linter.py`, handle the rule ID everywhere `scripts/build_rule_docs.py` special-cases rules: the sets `FORMAT_GATE`, `LEI_RULES` and `NEVER_PASS` where they apply, a branch in `examples()`, a branch in `status_logic()` and the limitations in `rule_page()` (`SOURCE_MODULES` and `UNTESTED_REGIMES` there are keyed by rule family, so a new family needs entries too). A format-gate rule also goes in `FORMAT_GATE_RULES` in `ci_outputs.py`, which keeps it out of the annotations and the summary table, and in the `COMMON.IXBRL_TAGGING` check in `docs/playground/app.mjs` that hides "Inspect section". If its issue messages can quote draft text, add it to `DRAFT_ECHO_RULES` in `ci_outputs.py`, so SARIF result messages use a fixed sentence instead (the job summary and annotations never print issue messages).
- **Generic rules without listed terms**: the rule-page generator builds its passing example from `required_terms` and `min_words` only. A generic rule that relies on `required_patterns`, or has no terms and `min_words=0`, needs its own branch in `examples()` in `scripts/build_rule_docs.py`, or the page build stops.
- **New section keys**: a rule that reads a new section key also needs a heading pattern in `SECTION_PATTERNS` (`document.py`), which the PDF, DOCX, Markdown and heading-based XHTML/HTML loaders use. For numbered-field XHTML it needs a mapping in `numbered_fields.py` for each regime it applies to: `_PART_SECTIONS` for a lettered part, or `_SUMMARY_SECTIONS` for a leading field (as `summary`, `risk_warning`, `management_statement` and `notification_date` are; `language` is found by its field label). Without them those loaders never fill the key, so a rule on the generic checks always reports missing for those drafts.
- **Playground dependencies**: the playground installs the wheel with `deps=False` (`docs/playground/runtime.mjs`) and loads lxml only on the first XHTML check; pypdf and python-docx are never available there. The modules `docs/playground/lint.py` reaches on the JSON path (the package `__init__.py`, `linter`, `report`, `whitepaper`, `anchors`, `lei`, `document`, `citations`, `rules/`) must not import lxml, pypdf, python-docx or a new third-party package at module level, directly or by importing `ixbrl.py`, `xhtml_parser.py`, `numbered_fields.py` or `collaboration_workspace.py` (which import lxml at the top) or `cli.py` (which imports `collaboration_workspace.py`). No automated check runs Pyodide, and the pytest suite has every dependency installed, so a break here goes unnoticed.
- **Draft-supplied metadata**: every top-level JSON key other than `title`, `type` and `sections` becomes `Whitepaper.metadata`, which rule logic reads. Only the keys in `_RESERVED_METADATA_KEYS` (`whitepaper.py`) are stripped, and the JSON loader forces `ixbrl_validated` to false. A new trust or validation flag must be added there, or a draft can certify itself (see the self-certification test in `tests/test_playground_bridge.py`).
- **Fail Closed**: Compliance checks must fail closed on missing sections. `ANNEX_II.G.DEPOSIT_FLOOR_REVIEW` never returns pass (`_deposit_floor_finding` has no pass branch). `COMMON.IXBRL_TAGGING` never passes for any loaded draft: JSON and the other draft formats give missing, and XHTML stays at review because `validate_ixbrl` never returns an empty issue list (when the namespace checks pass it still adds the tag-completeness note). `_ixbrl_finding` itself has a pass branch for an empty list, so a change to `ixbrl.py` must keep at least one issue or the gate opens.
- **Citations**: `Rule.citation` uses the canonical German form (e.g. `Art. 6 Abs. 7 MiCAR`). A newly cited act needs an entry in `ACT_URLS` in `citations.py` and, unless it is a `VO (EU)` regulation or its name is already English (as `MiCAR` is), an English name mapping in `to_english()`. For every rule citation, `tests/test_citations.py` checks that no listed German drafting term or doubled comma survives the conversion, that the numbers survive, and that at least one EUR-Lex link results (MiCAR's when MiCAR is cited); `test_known_conversions` pins the exact output of five fixed citations. It does not catch a second act missing from `ACT_URLS` or an untranslated act name, so check `source_urls()` and `to_english()` for the new citation, or add a `test_known_conversions` case.
- **Stable rule IDs**: rule IDs are stable identifiers (`rules/base.py`): add new rule IDs, never rename existing ones. They key SARIF results, the rule-page URLs and review bundles.
- **Report language is load-bearing** (CONTRIBUTING.md): the blocker and lawyer sign-off wording is tested in `tests/test_cli.py`. Never describe a pass as compliance.
- **Synthetic data only**: CONTRIBUTING.md requires fictional fixtures in `examples/`; keep tests, playground samples and the starter template the same way. Add no real white paper text, issuer or token names, IBANs or wallet addresses there (the examples name only public networks and authorities, such as Ethereum, BaFin and EBA). Real register data lives only in the study under `studies/` (see section 2); `docs/research/` names real vendors and products as market research.
- **Owner-reserved work**: `TODO(human)` marks code reserved for the owner, such as `displayCitation` in `docs/playground/model.mjs`. Leave it, and leave the items under "Needs owner decision" in `docs/research/adaptation-plan.md` to the owner.
- **Changelog and flags**: record user-facing changes under "Unreleased" in `CHANGELOG.md`, and document every new `cli.py` flag in `docs/API.md` (no test enforces either).
- **Older docs**: `docs/ARCHITECTURE.md` still says rules inherit from `BaseRule`, and it and `docs/FEATURES.md` use compliance wording ("compliant parameters", "regulatory rejection"). `docs/rule-extension-guide.md`, `docs/TESTING.md`, `docs/SETUP.md` and CONTRIBUTING.md describe the rule steps, `make check` and output paths more narrowly than this file. Where they disagree with this file or the code, the code wins. Some shipped output names also say "compliance" (the audit log title, `compliance-checklist.md` in the review bundle); they are fixed file and section names, not verdicts.

## 5. Files to Protect
Do not casually modify:
- `src/micar_linter/rules/base.py`: Core rule data types (`Severity`, the frozen `Rule` dataclass, `Finding`) that the whole package imports.
- `pyproject.toml` and `uv.lock`: Build and lock configs. CI installs with `uv sync --locked`.

## 6. Generated and Committed Outputs
Do not edit these by hand. Regenerate them after the change that affects them:
- `docs/rules/*.html`: run `uv run python scripts/build_rule_docs.py` after any change to rules, `citations.py`, `lei.py` or the special-rule logic in `linter.py`, because the pages embed their output. `tests/test_rule_docs.py` fails on stale pages and lints every example on them.
- `docs/playground/micar_whitepaper_linter-<version>-py3-none-any.whl`: after any change under `src/`, delete the wheel and run `uv build --wheel -o docs/playground/`. `tests/test_playground_wheel.py` checks that it matches the source, the project version and `docs/playground/index.html`. A local, untracked `docs/playground/.gitignore` containing `*` hides new files in that folder from `git status`; use `git add -f` for a wheel with a new name.
- `docs/playground/samples.json` and `docs/playground/sample-numbered.xhtml`: run `make playground-samples` after editing the examples they are built from.
- `examples/review-bundle/` and `reports/sample-*.txt`: committed sample outputs, as of their last refresh. `examples/review-bundle/` is a copy of the `make review-bundle` output for `art-stablecoin.json` (that target writes to the git-ignored `dist/review-bundle/`). `reports/sample-art-pass.txt` and `reports/sample-incomplete-blockers.txt` are copies of `micar-lint` text reports for `art-stablecoin.json` and `incomplete.json`. `tests/test_reserve_rules.py` reads `review-table.json` and `sample-art-pass.txt`; no test reads `sample-incomplete-blockers.txt`. They are refreshed by hand and can lag behind the code: no test compares them with fresh output. The "Real output" block in `README.md`, `docs/sample-review-bundle.md` and `docs/demo.svg` are hand-maintained copies of CLI output too, and `docs/linter-output.svg` is a styled mock-up of it. They go stale after any change to rules, report or bundle wording, or to `examples/art-stablecoin.json` or `examples/incomplete.json`; refresh them together.
- `studies/2026-07-title-ii-annex-i-whitepaper-study/` outputs (commands in its README): `python -m micar_linter.esma_register` writes `source-manifest.json` from `sample-manifest.csv`; `micar-lint-batch` writes `findings-pseudonymous.json` and `.csv` from the git-ignored `.study-cache/` (absent in a fresh checkout); `micar-study-report` renders `findings-summary.md` from that JSON; `micar-review-summary` writes `human-review-summary.json` from `human-review-matrix.csv`. Do not hand-edit these outputs. The `human-review-*.csv` files are worksheets for human reviewers under `review-protocol.md`; never fill them in yourself. A change to the study detector in `batch.py`, to `document_loader.py`, `document.py` or `study_report.py` leaves the findings stale until the study is re-run with its cache. `tests/playground/model.test.mjs` checks the study figures in `docs/playground/index.html` against the committed findings.
- The version appears in `pyproject.toml`, `uv.lock` (run `uv lock`, or CI's `uv sync --locked` fails), `src/micar_linter/__init__.py`, `CITATION.cff` (with `date-released`), the playground wheel's filename, `docs/playground/index.html` and every page in `docs/rules/` (regenerate them).

## 7. Git and Branching Rules
Do not merge feature branches into `main`, `master` or `develop`, and do not push to those remote branches, unless the user approved it in the current session or the change goes up as a pull request for review. These branches deploy; an unreviewed merge cannot be recalled.

Before proposing a merge or push, run `make check` on the feature branch. It runs ruff, the pytest suite (which asserts several of the `*.v1` output schema identifiers), the CLI smoke run, the review bundle, the playground checks and the starter-template contract. CI runs only on pushes and pull requests to `main`, so on a feature branch `make check` is the only gate. The project has no database, so there are no migrations to validate.

The GitHub Action is released through tags (`v1`, `v1.0.0`, `v1.1.0`, `v1.1.1`) that are separate from the package version tags (`v0.1.0` to `v0.2.1`). Users and the starter template pin `@v1`, so moving `v1` changes the Action for every user. `scripts/check_whitepaper_starter.py` requires the starter workflow to keep the exact lines `uses: sebastianfoerste/micar-whitepaper-linter@v1`, `whitepaper: whitepaper.json` and `strict: 'false'`. The Action runs `uvx` without the `docx` extra, so DOCX input fails there even though its `whitepaper` input description lists DOCX, and `--coverage` in `extra-args` stops the run before `--strict` and the CI outputs (see section 3).
