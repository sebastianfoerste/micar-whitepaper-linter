The first two are fixed: the state is saved before every XObject and restored after it, and each array inside a `/VE` expression is read through once for each depth, with the same result; the third is listed among the limits below.

## Context

White papers identify their parties by Legal Entity Identifier. The repo's study maps the LEI to Annex I, Part A (`ANNEX_I_PART_A_05_LEI_OR_IDENTIFIER` in `batch.py`). A mistyped LEI is a common, mechanical error that a deterministic check can catch. WhitePaperXBRL checks LEI check digits and optionally asks GLEIF, but treats a failed lookup as valid (Observed in its docs); that fails open. EUR-Lex was unreachable, so no new citation could be verified.

## Options

1. One rule, check digits only.
2. Two rules: check digits, and consistency between the party sections and the rest of the draft.
3. Option 2 plus a GLEIF registry lookup.

## Decision

Option 2, offline.

- **`COMMON.LEI_CHECK_DIGITS`** (MAJOR) reads the text of every section and, for a document file, the whole text of the file (`lei.py`):
  - **LEI-shaped codes.** A run of 20 characters, 18 upper-case ASCII letters or digits and then two digits, that is not part of a longer run of ASCII capitals and digits. Each has its check digits checked (`lei.find_leis`).
  - **Texts that read LEIs** (`lei.reads_leis`): the party sections (`issuer`, `offeror`, `trading_platform_operator`), and any text that names an LEI label or holds an LEI-shaped code with a letter, as written or as shown (below). The label is LEI or LEIs as a word ("LEI-Nr.", "LEI code"), legal entity identifier(s) or legal entity ID, or Rechtsträgerkennung(en) (also Rechtstraegerkennung, and with the umlaut decomposed into "a" and U+0308), in any case. Any spaces, hyphens, dashes or line ends may stand between the words of the long labels, and a hyphen, a dash, a soft hyphen or a line end (with or without a hyphen) between any two of their letters, as a PDF or a word processor breaks a word ("Rechtsträger-\nkennung").
  - **A draft that reads LEIs reads them in all its text** (`lei.draft_reads_leis`): once it has a party section, or one of its sections or the text of its file reads LEIs, every section is read as a text that reads LEIs, and so is the text of a PDF, DOCX, Markdown, XHTML or HTML file outside its sections. The document loaders keep that text under the reserved metadata key `document_text`, which a JSON draft cannot set: for a PDF every extracted line, headings, running headers and text drawn invisibly included; for a DOCX every paragraph of the body, of its tables and text boxes, and of the headers and footers each section defines, tracked insertions, text moved away under tracked changes (`w:moveFrom`) and any `w:t` inside a tracked deletion included; for Markdown the file as written (read as shown too, below); for XHTML and HTML every text that lxml's HTML parser keeps outside the head, scripts, styles and templates, a line per block element and `<br>` (table cells, definition lists, spans, sections, headings and hidden iXBRL facts included), and for a saved iXBRL viewer page that of the markup it packs; after it, for every format, the text of each section that the draft's regime drops (see the limits). That parser drops a CDATA section and does not expand an entity that a document declares in its own DTD (see the limits). This text holds hidden text as if it were shown (a DOCX run marked hidden, text a DOCX has moved away under tracked changes and any `w:t` inside a tracked deletion, PDF text that is drawn but cannot be seen, XHTML or HTML text that CSS or the `hidden` attribute hides), so a DOCX, PDF, XHTML or HTML file is also read as a reader sees it (below). So a code in a heading, in a DOCX paragraph that the loader takes for a heading because it has no lower-case letter, in a Word list item, in a table cell, on a PDF line that the loader reads as a heading or that drops out of every section, under a Markdown sub-heading, or in a section that is not a party section and names no LEI, is read. A code of the file text that no section holds (`lei.codes_outside_sections`) is named "outside the section text (in a heading, a table, a header or footer, or text in no section)". Only an LEI-shaped code as written in a section that reads LEIs on its own counts as found (below): one elsewhere adds an issue when its check digits fail, and never lets a draft without such a code pass.
  - **Each text is read as written and as shown** (`lei._shown`). Where markup or a character reference changes a text that is read (a section, or the text of the file), it is read a second time as a Markdown or HTML renderer shows it: HTML comments (from `<!--` to the next `-->`) and tags removed, a block tag (`p`, `div`, `li`, `td`, `tr`, `h1` to `h6` and the like) and `<br>` shown as a line end; character references (`&nbsp;`, `&#160;`, `&thinsp;`, `&ndash;`, `&shy;`, `&#8203;`) replaced by the characters they name; every run of asterisks, backticks or tildes, every bracket, every link target (`](…)`, `][…]`) and every backslash before punctuation or a line end removed; and every run of underscores at the edge of a word removed, while one inside a word ("snake_case") stays. This removes more than a CommonMark renderer does (an asterisk that is no emphasis, a reference inside a code span); since the text is read as written too, removing more only adds codes. Everything below applies to each reading. A malformed code of the shown reading is named in its section and quoted as shown ("9999 SYNT H000 0ZZQ 026" for `9999&nbsp;SYNT&nbsp;…`); an LEI-shaped code of either reading has its check digits checked. Only an LEI-shaped code as written counts as found (below), so a valid LEI that markup splits as written ("9999SYNTH**0000ZZQ0263**") adds no issue and does not count as found either.
  - **Each DOCX, PDF, XHTML or HTML file is also read as a reader sees it** (`lei.codes_only_as_shown`). The loader reads the whole text of the file a second time without the text it finds a reader cannot see, and keeps that reading under the reserved metadata key `shown_text`, which a JSON draft cannot set, where it differs from `document_text` (so a file without such text is read as before). A code that is malformed or fails its check digits in either reading keeps the rule from passing: hidden text that the second reading leaves out can no longer complete a code that the document shows malformed ("9999SYNTH0000ZZQ02" shown and "63" hidden), split it into groups that are no LEI-like code (a hidden "/" inside it; but see the limits for a separator under 1 pt) or glue it to other text. Hidden text that still takes up its room on the page leaves a gap where it stands: in a DOCX, a run that Word lays out but that cannot be seen (white, or under 1 pt); in a PDF, all of it, as the text position moves past it as past shown text; in XHTML or HTML, text that `visibility` hides, which stands as a space. The DOCX and PDF readings put a zero-width space there, which the code reading takes for nothing between two groups, so a hidden "/" between two groups that the page shows apart cannot join them into one valid code: "9999SYNTH 0000ZZQ0263", as the page shows it, reads as a code split into groups. Text that is left out of the page (`w:vanish`, a tracked deletion or move away, and the other XHTML and HTML hiding below) leaves no gap, as the page joins what stands on either side of it. Text under 1 pt takes next to no room, so the page shows no gap where it stands, but the reading leaves one there all the same: inside a valid code that gap can only add a review (a false Review, below), and inside a malformed code it can split the code into groups that are no LEI-like code, so that the code is not read (a limit below). Where reading the file as a reader sees it fails for any reason, that reading is dropped and the file is read as without it, as before the amendment; as it only adds issues, dropping it is never less strict than `main`. A code of that reading that neither a section nor `document_text` holds is named "in the text as a reader sees it (without hidden, deleted or moved-away text)"; one they hold is named as there. Its LEI-shaped codes do not count as found (below), and a label in it makes the draft read LEIs, so the reading can only add issues: text it wrongly takes for hidden costs at most a false Review. It leaves out:
    - in a DOCX (`document._docx_texts`, `document._DocxLook`), text inside a tracked deletion (`w:del`) or moved away under tracked changes (`w:moveFrom`), and a run, with everything in it (such as a text box), that is hidden (`w:vanish`), set in a font under 1 pt (`w:sz` under 2 half-points) or with its characters scaled to under 1 pt wide (`w:sz` times the character scale `w:w` under 2 half-points at 100 %; 10 pt where no `w:sz` is set), or white or nearly white (`w:color`, each colour channel at least 95 %) with no background behind it. A background is a highlight (`w:highlight` other than `none` and `white`), run shading, or the shading of the table cell the run stands in (the cell's own `w:shd`, else that of its table style; only where neither sets one, that of the cell around a nested table, so that a nested cell's own shading counts even where it is white or sets no fill, which can only add Reviews): the fill of clear or patterned shading (`w:shd`), or the colour of solid shading, in which automatic stands for black; `nil`, no fill (`auto`) and white or nearly white are none. A colour, fill or pattern colour that names a theme colour (`w:themeColor`, `w:themeFill`) is taken from the document's theme through its colour mapping (`background1` is light 1, white in Word's default theme), with its tint or shade mixed in channel by channel; without a theme, light 1 is white and dark 1 black, and a comment or processing instruction in the theme's colour scheme is passed over. Each property counts as set on the run, else in its character style, else in its paragraph's style (the default paragraph style for a paragraph without one), else in the run properties of the table style of the table it stands in (the default table style for a table without one), else in the document defaults, each style with the styles it is based on (a `w:basedOn` chain that comes back to a style on it stops before that style; each style is resolved once, however long its chain); the table style counts after the paragraph style as well, and the run is hidden if either order hides it. `w:vanish` set in any of these styles or in the defaults hides the run unless the run sets it off itself, as Word toggles it in styles. A paragraph whose mark is deleted, moved away or set to `w:vanish` on the mark itself runs on into the next one. What stays joins as Word shows the document with every tracked change accepted ("No Markup"): a tracked insertion, a move's new place, a content control, a field result, a smart tag, custom XML and a hyperlink are read where they stand, so a code split between a run and one of them reads as one, in the body, its tables and text boxes and the headers and footers. The section text and the regime are read as before;
    - in a PDF (`document._PdfInk`, `document._OptionalContent`), text drawn in text render mode 3 (invisible, as in an OCR layer) or 7 (clipping only); text that every colour its render mode paints draws white or nearly white (the fill for modes 0 and 4, the stroke for 1 and 5, both for 2 and 6; a colour set with `g`, `rg` or `k`, their stroke forms `G`, `RG` and `K`, or with `sc` or `scn` in the colour space that `cs` or `CS` sets, which counts where it is `/DeviceGray`, `/DeviceRGB` or `/DeviceCMYK`, or a name in the page's or form's `/ColorSpace` resources that stands for one of them, for an ICC-based space by its number of components or for a calibrated grey or RGB space (`/DeviceGray` until one is set); each grey or RGB component at least 0.95, each CMYK component at most 0.05); text whose glyphs are under 1 pt high or wide on the page (the `Tf` size, for the width times the horizontal scaling `Tz`, scaled by the text matrix, the current transformation matrix and the matrix of each form XObject it is drawn in, the height measured across the baseline, so that glyphs a text matrix slants flat count too); and text inside marked content tagged `/OC` (`BDC`) or in a form XObject with an `/OC` entry whose optional content the document's default configuration (`/OCProperties /D`) does not show: an optional content group that its `/OFF` array names, or that its `/BaseState /OFF` leaves off without its `/ON` array naming it, and a membership dictionary by its visibility expression (`/VE`), else its policy (`/P`, `/AnyOn` by default) over its groups; an `/OC` entry that names neither, and an expression nested more than 32 deep or read through more than 10 000 times, counts as shown. The graphics state follows `q` and `Q`, and it is saved before every XObject that `Do` draws and restored after it, so nothing that a form's content sets outlasts the form: also where the form's entries cannot be read (a `/Matrix` that is not an array of six numbers, a string of six digits included, leaves the matrix as it was for the form's content, and `/Resources` that are not a dictionary, or are empty, are those of the content around it), and where pypdf reads the content of an XObject whose `/Subtype` is not `/Form` (it reads that of every XObject but an image). An operator whose operands this reading cannot read (a number too large for a float as an operand of a colour operator, `cm`, `Tf`, `Tr` or `sc`/`scn`) leaves the state as it was. Where pypdf itself cannot read an operand (a number too large for a float as the operand of `Tz`, `Tw`, `TL`, `Td` or `Tm`, among others), pypdf stops and the file cannot be read, as on `main`. A page without resources of its own takes those of the page tree above it, and none where a `/Parent` is no dictionary. Each optional content group, membership dictionary, `/OCGs` array and `/VE` expression is read once, by its object number or, given directly, by the object itself, however often the content names it, and each array inside a `/VE` expression is read through once for each depth at which it is reached, however many membership dictionaries share it: the operands read in full are kept with what each took from the 10 000 reads, and a later reading takes as many of them as the reads it has left allow (a binary search) and reads on from there, so it reads as a first reading would. pypdf calls its operator visitor with the operands it then reads, so the loader replaces the text of each such operator by a zero-width space (the gap above) before pypdf reads it, on a second extraction of each page that draws such text; a page without it is extracted once;
    - in XHTML or HTML (`xhtml_parser._shown_flow`), what `document_text` reads, without: `<noscript>` and the content of `<iframe>`, `<canvas>`, `<object>`, `<video>`, `<audio>` and `<embed>`, whatever their style; inside an `<svg>`, the elements an SVG drawing does not render where they stand (`<desc>`, `<title>`, `<metadata>`, `<defs>`, `<symbol>`, `<clipPath>`, `<mask>`, `<pattern>`, `<marker>`, `<linearGradient>`, `<radialGradient>`, `<filter>`, `<style>`, `<script>`); an element that its `style` attribute sets to `display:none`, or, inside an `<svg>`, whose `display` attribute is `none` where that `style` attribute sets no display; where neither sets a display, an element with the `hidden` attribute (other than `until-found`), one that the HTML user agent style sheet hides (`<area>`, `<base>`, `<basefont>`, `<datalist>`, `<link>`, `<meta>`, `<noembed>`, `<noframes>`, `<param>`, `<rp>`, `<title>`) and a `<dialog>` without the `open` attribute, each with all its content and line breaks; all but the first `<summary>` child of a `<details>` without the `open` attribute; the content of an element set to `content-visibility:hidden`, or with `hidden="until-found"` where the `style` attribute sets no `content-visibility`; and the text of an element set to `visibility:hidden` or `visibility:collapse` (inside an `<svg>`, also by its `visibility` attribute where the `style` attribute sets none), or inside one without `visibility:visible` of its own, which keeps its place and so stands as a space. Only the `style` attribute is read, as CSS reads it and in one pass over it: comments (to `*/` or the end), strings and escapes count as in CSS, a declaration whose value is invalid (`display:bogus`) is dropped, and so is one whose value uses a function, such as a custom property through `var()` (`--h:none; display:var(--h)`), which CSS applies (see the limits); the last valid declaration of a property counts, and one marked `!important` wins over those without the mark; `revert` and `revert-layer` count as no value, `initial` as `visible` and, with `unset` and `inherit`, as a display other than `none`.
  - **LEI-like codes** (`lei.lei_like_codes`, `lei._codes`). In a text that is read, every LEI-like code counts, wherever it stands. The text is split into groups, the runs of letters and digits of any script with any marks of the Basic Multilingual Plane among them (Unicode category M: combining accents, variation selectors such as U+FE0F), so a look-alike (a Cyrillic "Ѕ", a full-width digit, an "S" with a combining accent) stays inside the code it stands in. The character classes come from the Unicode database of the Python that runs the linter. An LEI-like code is:
    - one group of 16 to 24 characters that holds a digit or is in ASCII capitals; or a longer one that holds a digit and either starts with "LEI" in any case and has at most 28 characters (a code glued to its label, "LEI9999SYNTH07000ZZQ02637"), or leaves 16 to 24 characters with a digit once a word glued to it is taken away: its leading letters, its leading letters up to the last lower-case one ("KennungSYNTH…"), its trailing letters, or both ("Kennung9999SYNTH0000ZZQ026", "Code9999SYNTH07000ZZQ0263", "9999SYNTH0000ZZQ0263Kennung");
    - groups joined by any number of invisible characters and up to three spaces (no-break and thin spaces included), hyphens or dashes or line ends, with at most one hyphen or dash and one line end in each gap (so invisible characters alone join two groups too, as a left-to-right mark between "9999SYNTH" and "0000ZZQ0263" does), that together hold at least 16 characters and a digit, or whose groups all have the same length ("XXXX XXXX XXXX XXXX XXXX"). Invisible characters are every format character (Unicode category Cf: zero-width space, non-joiner and joiner, word joiner, left-to-right and right-to-left marks, bidirectional embeddings, overrides and isolates, invisible operators, the soft hyphen, the Mongolian vowel separator, the Arabic letter mark, the byte-order mark), every control character other than whitespace, and every mark outside the Basic Multilingual Plane. Hyphens and dashes are every dash of Unicode category Pd (hyphen-minus, hyphen, non-breaking hyphen, figure dash, en and em dashes, horizontal bar, two-em dash, small em dash, small and full-width hyphen-minus, and the other dashes), the minus sign, the hyphen bullet and the middle dots (U+00B7, U+2027, U+30FB and U+FF65). A group of 16 or more characters, and "LEI" or "LEIs" in any case, do not join. A group of letters only that holds a lower-case letter or a letter outside ASCII is a word, and joins only beside a group of the same length that holds a digit, as in a code in lower case split into groups ("9999 synt h000 0zzq 0263"); or
    - two pieces of a code that a narrow table cell wraps onto the next line, with the words of the next cells between them, as pypdf extracts a table laid out line by line ("Offeror LEI 9999SYNTH0000 Synthetic Offeror GmbH" / "ZZQ026 Frankfurt am Main"): a piece is one group of fewer than 16 characters that holds a letter and a digit, and a piece on a line that names an LEI label, or on the line before one, makes a code with the longest piece on the next line if the two hold at least 16 characters together.

    One that is not LEI-shaped as written is malformed (`lei.malformed_leis`): it has 16 to 19 or 21 to 24 characters, is in lower case, has a letter where a check digit belongs or a character outside ASCII, is glued to a leading "LEI" or to a word, is split into groups, or is two pieces of a wrapped code. The issue quotes it as its reading gives it, with each run of spaces, invisible characters or line ends as one space, cut after 40 characters, so neighbouring groups that joined it ("CODE 9999 SYNT H000 0ZZQ 0263 HRB 12345") are quoted with it; two pieces are quoted with an ellipsis between them ("9999SYNTH0000 … ZZQ026").
  - **Where this departs from the reading recommended by the verification** (every case-insensitive run of 18 to 22 letters and digits, or spaced groups that join to that length, in a section with a label), and why:
    - A run of letters only that holds a lower-case letter, or a letter outside ASCII, is a word, not a code. `examples/art-stablecoin.json` names "Aktiengesellschaft" (18 letters) in its labelled issuer section, so the recommended reading sends that example to Review; German legal prose is full of such words ("Handelsregisternummer", "aufsichtsrechtlichen"), and so are German headings in capitals ("RECHTSTRÄGERKENNUNG"). An LEI holds only ASCII letters and digits, and its last two characters are digits.
    - A word joins groups only beside a group of its length with a digit. If every word joined, prose such as "with a fictional registered seat and business address at Example Street 22" in the labelled offeror section of `examples/other-crypto-asset.json` would be one code and send that example to Review; if every word of up to four letters joined, "was founded in 2019 and has its seat in Berlin" would read "in 2019 and has its seat in" as a code of 21 characters.
    - A run of groups in capitals without a digit counts only if all its groups have the same length, so a heading in capitals ("INFORMATION ABOUT THE OFFEROR") is no code.
    - Groups count from 16 characters with no upper bound, so a spaced code with its neighbours ("LEI CODE 9999 SYNT …") is read; one group of more than 24 characters (28 for one with a digit after a glued "LEI"), such as a contract address or a hash, is not.
    - The whole text of a draft that reads LEIs is read, not only the sections that name an LEI, and not only the section text: a loader's heading detection and section boundaries are heuristics, and what they leave out must not hide a code.
    - Two pieces of a wrapped code make one code only where each is one group with a letter and a digit and one of their two lines names an LEI label. Read with groups of digits or capitals only, with spaced groups or without the label, codes on consecutive lines that are no LEI give Review in a draft that reads LEIs: the DTI and the functionally fungible group DTI of the template (9 characters each), a VAT number over a register number, and in `examples/review-bundle/compliance-checklist.md`, which names the LEI rules in lines with "ISO/IEC 7064 MOD 97-10" and rule IDs in capitals, thirteen false codes that changed its `--json` report.
    - The shown reading is read besides the text as written, not in its place: text a renderer does not show (an HTML comment, a link target) may still hold a code, and the written reading keeps apart what removed markup glues together.
  - **Limits: a code that is not seen**, so the rule can still pass while it is malformed or invalid:
    - Text the loaders do not extract: in a DOCX, footnotes, endnotes, comments, deleted text as Word writes it (`w:delText`), field codes and text in charts, SmartArt or images; in a PDF, text that pypdf does not extract (images, scans, annotations, form fields); in XHTML or HTML, the head, scripts, styles and attribute values (alt or title text); in a JSON draft, everything outside `sections` (the title, other keys).
    - A code that is no LEI-like code: one group of fewer than 16 characters, or of more than 24 (28 for one with a digit after a glued "LEI") that no glued word explains, such as a code with digits glued to it ("…026312345") or a code that starts with letters glued to a word with no lower-case letter before a capital at the join ("kennungsynth…", "CODESYNTH…"); groups that together hold fewer than 16; one group of letters only with a lower-case letter or a letter outside ASCII; groups split by any other character (a full stop, a slash, a comma, an underscore that is shown, a bullet), by more than three characters other than invisible ones, or by two hyphens or dashes or two line ends (a blank line); a code split into groups where a word stands beside no group of its length with a digit ("9999 synt habc defg h012"); groups in ASCII capitals without a digit and of different lengths; a code that a table cell wraps where a piece holds no letter or no digit or is split into groups, where neither line names an LEI label, where the two pieces are not on consecutive lines, or where the code wraps over more than two lines.
    - Markup or a reference inside text that a renderer does not show (an HTML comment, a tag's attributes, a link target) is read as written only, and a renderer that shows markup otherwise than `lei._shown` reads it (for example a reference it does not know) may show a code that neither reading sees.
    - A mark outside the Basic Multilingual Plane right after the last character of an LEI-shaped code counts as an invisible character after the code, not as part of it, so that code is still LEI-shaped.
    - XHTML CDATA sections: lxml's HTML parser, which reads every XHTML and HTML file for the sections, the numbered fields and the document text, drops a CDATA section as it drops a comment. A code inside `<![CDATA[…]]>` is not read, and a code with part of it in one is read without that part (`LEI: 9999SYNTH<![CDATA[0000ZZQ026]]>` reads as "LEI: 9999SYNTH", which holds no LEI-like code), so the rule can pass.
    - Entities that an XHTML or HTML document declares in its own DTD (`<!DOCTYPE html [<!ENTITY offlei "…">]>`) are not expanded: the text keeps the reference (`LEI: &offlei;`), so a code given through one is not read.
    - Hidden text that the reading as a reader sees it (above) does not tell apart is read as if it were shown, so a fragment there can complete a code that the document shows malformed ("9999SYNTH0000ZZQ02" shown and "63" hidden reads as the valid "9999SYNTH0000ZZQ0263"), or split it into groups that are no LEI-like code, and no issue names the code. That reading tells apart only what is listed above. Among what it does not tell apart: in a DOCX, text in a font of 1 pt or more whose characters are 1 pt wide or more, text in the colour of a coloured background (such as black on black paragraph shading), text that conditional table formatting (`w:tblStylePr`) hides, characters condensed onto each other by their spacing (`w:spacing`), text raised or lowered out of view (`w:position`), text in a complex-script run whose size (`w:szCs`) is tiny, a run with `w:specVanish`, a `w:t` that stands in the code part of a complex field (between its `begin` and `separate` field characters), which Word does not show, and text behind an image or a shape or off the page; in a PDF, text in a font of 1 pt or more (also where an `ExtGState` `/Font` entry sets it under 1 pt), text under other content (such as a white filled rectangle) or outside the clipping path or the page, transparent text (an `ExtGState` alpha or a soft mask), text in a pattern, white text in another colour space (Lab, separation, DeviceN, indexed), and optional content that only a configuration other than the default or the usage settings turn off; in XHTML or HTML, text that a style sheet hides (a `<style>` element or linked CSS, through a class or any other selector), text that other properties hide (`opacity`, `color`, `font-size`, position, clipping, transforms), a `display` or `visibility` that a custom property gives through `var()`, SVG text without fill or with a zero opacity, the options of a `<select>` other than the one it shows, MathML annotations, and text hidden by scripts. A group shown with fewer than 16 characters is no LEI-like code (below), so hidden text that completes such a group, or that hides every other character of a valid code, leaves the reading as a reader sees it no code to name. Where such text completes the code, the rule passes unless something else keeps it from passing, such as another malformed code or no LEI found in a section (above). The DOCX section text holds only the runs and hyperlinks directly in a paragraph of the body (python-docx's `paragraph.text`), so text Word shows there in a tracked insertion or at a move's new place (`w:moveTo`), a content control, a field result, a smart tag, custom XML or a text box is not section text: a valid code that such text completes with four characters or fewer reads as malformed in the section text, and the rule goes to Review, which fails safe. That holds in a section the draft's regime drops too: the loader drops the sections of the other regimes (an ART draft its `emt`, `crypto_asset` and `not_approved_statement` sections, an EMT draft its `art` and `crypto_asset` sections, any other draft its `art` and `emt` sections, whether the regime is inferred or given with `--type`), and it keeps the text of each dropped section, as the section text reads it, after the text of the file and a blank line apart from it, so the rule reads a code there as the section shows it, and a code that a dropped section shows malformed goes to Review whatever the regime (a code there still never counts as found); the reading as a reader sees it covers a dropped section as it covers the rest of the file. Before, the rule read such a code only in the text of the file, which joins to it text moved away or deleted (which the reading as a reader sees it leaves out, but only where that reading does not fail) and text in a tracked insertion, a content control, a field result or a smart tag, so a change in how the regime is inferred could change the result, as when an Annex I draft came to be read as an ART.
    - A hidden separator under 1 pt (a DOCX run in a font under 1 pt, PDF glyphs under 1 pt) takes next to no room, so the page shows no gap where it stands, while the reading as a reader sees it leaves a gap there, as for all hidden text that takes up its room. Inside a malformed code, that gap can split the code into groups that are no LEI-like code, such as a word of letters only beside a group of another length (a "/" in a half-point font after "hwupkr" in "hwupkr0mpou8fgxbt394", which the page shows whole), so the code is not read in either reading and the rule can pass, as in 1.2.1 and before the amendment of 2026-11-04. The same "/" left out of the page (`w:vanish`) leaves the code whole, so the rule goes to Review.
    - A PDF party table whose LEI label stands only in a header row ("Party Name LEI Seat") above the data row in which the code wraps inside its cell ("Offeror Synthetic Offeror GmbH 9999SYNTH0000 Frankfurt" / "ZZQ026 am Main"): only a piece on a line that names an LEI label, or on the line before one, pairs with the next line, so the two pieces are not read as one code and the rule can pass, also when another row of the table holds a valid LEI.
  - **False Reviews**, which fail safe: every LEI-like code in a draft that reads LEIs counts, wherever it stands, so an IBAN (with or without spaces, "DE00 0000 0000 0000 0000 00", "RO00SYNTH00000000000000"), a long number in groups, a placeholder such as "XXXXXXXXXXXXXXXXXXXX", a reference number of 16 to 24 letters and digits, an address or heading in capitals with a digit in it, a word of 16 to 24 ASCII capitals in any heading or text ("INTERESSENKONFLIKTE"), numbers in neighbouring table cells or lines that join (in an HTML table of a Markdown draft too, whose cells the shown reading puts on lines of their own), two groups with a letter and a digit on a line that names an LEI label and the next line that together hold 16 characters, a word with a digit of more than 24 characters that a glued word explains ("Kryptowertetransfer2024Verordnung"), a valid LEI glued to "LEI" or to a word or split into groups (also by markup, as written), or a code that the file text and a section quote with different neighbours (named twice, and once more where the file's text as a reader sees it quotes it with other neighbours) gives Review; a 20-digit number anywhere in such a draft has its check digits checked. So does text that the reading as a reader sees it takes for hidden while a reader sees it, where leaving it out glues, splits or shortens a code, and hidden text that takes next to no room, where the gap it leaves splits a code. Among such text: in a DOCX, white text on paragraph or table shading, on shading that conditional table formatting sets, or on a coloured page, image or shape, white text on patterned run shading whose fill is white or automatic but whose pattern colour darkens it (such as `pct90` in black), white text in a nested table cell whose own `w:shd` sets no fill (`nil`, automatic) inside a shaded cell, a run whose paragraph style and character style both set `w:vanish`, which Word toggles back to shown, a run that its table style hides in only one of the two orders the reading tries, where Word uses the other, a complex-script run whose `w:sz` is under 2 half-points while its `w:szCs`, by which Word sizes it, is not, and a run under 1 pt inside a valid code; in a PDF, white text on a coloured background, and glyphs under 1 pt wide inside a valid code; in XHTML or HTML, an element that a style sheet shows although the `hidden` attribute, the user agent style sheet or a closed `<dialog>` hides it, fallback content that a browser shows, as in an `<object>` whose resource cannot be shown or a `<noscript>` or `<canvas>` where scripts are off, and SVG text in `<defs>` that a `<use>` element draws.

  Statuses:
  - Missing: no section that reads LEIs on its own holds an LEI-shaped code as written (a purely numeric one counts only there) and no party section has text other than a placeholder (fail closed). A malformed code, or one with invalid check digits elsewhere, is named in the issues and does not change this status.
  - Review: any LEI-shaped code that is read fails ISO/IEC 7064 MOD 97-10, an LEI-like code is malformed, or no section that reads LEIs on its own holds an LEI-shaped code as written while a party section has text. Point 5 of each party Part allows another identifier required pursuant to applicable national law in place of the LEI, and the rule cannot recognise one.
  - Pass: a section that reads LEIs on its own holds an LEI-shaped code as written, every LEI-shaped code that is read, as written or as shown, and in the file's text as a reader sees it, has valid check digits and no LEI-like code is malformed.
- **`COMMON.LEI_CONSISTENCY`** (MAJOR) looks only at LEI-shaped codes with valid check digits, so a single typo, or a malformed code, is reported once, by `COMMON.LEI_CHECK_DIGITS`; a draft with a malformed LEI next to a valid one can pass this rule by design. Statuses:
  - Missing: no party section (`issuer`, `offeror`, `trading_platform_operator`) has text other than a placeholder.
  - Review: a party section has text but none has a valid LEI; a valid LEI outside the party sections appears in none of them; or `issuer` names more than one LEI.
  - Neither of the last two counts an LEI that the draft gives for a person other than the parties, which the template of Implementing Regulation (EU) 2024/2984 asks for: the crypto-asset service provider in charge of the placing (Table 2 field E.31, Table 3 C.22), a custodian of the reserve assets (Table 3 G.8), and a person other than the issuer who offers the token, seeks its admission to trading or draws up the white paper (Table 3 AA.1 and AA.3, Table 4 A.27). The field label or the sentence that holds the code must name the role before it (`lei.other_person_leis`).
  - Pass: otherwise.
- **Citation.** `Anhang I Teil A Nr. 5, Teil B Nr. 5, Teil C Nr. 5, Anhang II Teil A Nr. 5, Anhang III Teil A Nr. 5 MiCAR`, checked against the Official Journal on 2026-10-27. Point 5 of each party Part names the LEI or another identifier required pursuant to applicable national law, and Art. 2(1)(b) and (c) of Implementing Regulation (EU) 2024/2984 ask for the LEI where available. Releases 1.2.0 and 1.2.1 cite Part A of each Annex without a point, although Annex I Part A covers the offeror, and report Missing where the amended rules report Review. The amendment reached `main` on 2026-10-29, after 1.2.1.
- **Anchoring.** Both rules anchor to the `issuer` section for line mapping, the SARIF log and the review table. The playground names "every section" in its place and offers no "Inspect section" button for them (`ALL_SECTION_RULES` in `docs/playground/model.mjs`).
- **CI outputs.** Issue text quotes the LEI, so both rules are in `DRAFT_ECHO_RULES` and the SARIF log uses the fixed sentence instead; the job summary and annotations print no issue text.
- **Network.** No registry lookup: a pass means the characters are consistent, not that the LEI exists or belongs to the named entity.

## Consequences

- Each regime gains two rules, and every existing report gains two findings. The three full synthetic examples carry a fictional LEI with computed check digits and pass both rules; `examples/incomplete.json` has none and shows both as Review, because its issuer section has text.
- Rule IDs are new; no existing ID, status, severity or exit code changes. `--strict` is unaffected, because neither rule is a BLOCKER.
- A JSON section given as a list or an object is read as its items or its "key: value" entries, one per line, nested ones too; before, the loader wrote Python's representation of it ("['…', '…']"), whose escapes turned a zero-width space or a line end into the letters `\u200b` or `\n` and so split a code or glued a letter to it. This changes the text every rule reads for such a section; a section given as a string is read as before.
- The 2026-11-02 amendment changes no rule ID, severity or exit code and adds no status: a draft that gives a malformed LEI-like code anywhere in its text, or an LEI-shaped code with invalid check digits outside a section that reads LEIs on its own, next to a valid LEI, moves from Pass to Review on `COMMON.LEI_CHECK_DIGITS`, and a 20-digit number anywhere in a draft that reads LEIs has its check digits checked; the false Reviews above can move a draft from Pass to Review too. `COMMON.LEI_CONSISTENCY` still reads the sections only. The seven drafts in `examples/` give the same `--json` reports as before.
- The 2026-11-04 amendment changes no rule ID, severity or exit code, adds no status and leaves `COMMON.LEI_CONSISTENCY` as it was: a DOCX, PDF, XHTML or HTML draft in which hidden text that the reading as a reader sees it leaves out completed, split or glued a code that the document shows malformed, or one with failing check digits, moves from Pass to Review on `COMMON.LEI_CHECK_DIGITS`, and the false Reviews above can move a draft with white or hidden text that a reader does see from Pass to Review too. A file without such text keeps no `shown_text` and is read as before; the seven drafts in `examples/` give the same `--json` reports as before. The DOCX loader builds the second reading in the walk that builds the first and resolves each style once, however long its `w:basedOn` chain; `xhtml_parser.document_texts` parses an XHTML or HTML file once for its two readings and walks the tree twice, reading each `style` attribute once from start to end (a comment or a string that is not closed runs to the end, so nothing is read again), while the loader as a whole calls the HTML parser four times for such a draft, as before (for the viewer-page check, the two texts, the numbered fields and the sections); the PDF loader follows every page's operators with a visitor, extracts a page that draws text that cannot be seen a second time, and reads each optional content group, membership dictionary, `/OCGs` array and `/VE` expression once, and each array inside a `/VE` expression once for each depth. - Each reading is one pass: the text is split into groups once, each group is classified once, each gap between two groups is looked at once (a gap of more than three characters only to drop its invisible characters), only the groups that can be part of a code are looked at again, the pieces of a wrapped code are paired line by line through the longest piece of the next line, and the label search reads each run of spaces or line ends once. The shown reading removes comments with one forward search per comment and the other markup with two regular expression passes. Its time grows linearly with the length of the text; in the tests, a label followed by 200 000 line ends is read in under the 1 s bound, and 200 KB of other text (labels and digits, groups, markup, table pieces, invisible characters, glued words among them) in under the 2 s bound. The result is kept for the last 64 texts read, so the two rules do not repeat it for the same text. The character classes are built once, on the first reading (about 20 ms here). ## Non-negotiables check

- Fails closed when there is no LEI. In a draft that reads LEIs, an LEI-like code anywhere in the text the linter reads that is not an LEI with valid check digits never lets `COMMON.LEI_CHECK_DIGITS` pass, and a draft that reads no LEIs has no LEI to pass on. What the rule cannot see is listed under the limits above: text the loaders do not extract (XHTML CDATA sections and entities a document declares in its own DTD among it), hidden text that the reading as a reader sees it does not tell apart (such as a PDF fragment under a white rectangle or an HTML fragment that a style sheet hides) where it completes or splits a code the document shows malformed, and a malformed code that is no LEI-like code in either reading (such as one that has lost five characters, one split by full stops, or one that a table cell wraps on lines that name no LEI label, as in a PDF party table with its label only in the header row). Such a code can pass, so the rule meets "a malformed or invalid LEI never ends in Pass" only for LEI-like codes in the text it reads. `COMMON.LEI_CONSISTENCY` leaves malformed codes to `COMMON.LEI_CHECK_DIGITS` by design.
- Deterministic, with no model and no network.
- Test LEIs are synthetic with computed check digits; no real identifier appears in the repo.
- The point 5 pinpoint was added on 2026-10-27 after the Official Journal check.
- Severity: MAJOR for both rules, confirmed by the owner on 2026-10-22.
- Owner decision of 2026-10-27: a party section without an LEI goes to Review, not Missing.
