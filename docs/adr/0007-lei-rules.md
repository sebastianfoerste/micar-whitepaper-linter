# 0007. LEI check-digit and consistency rules

Status: Accepted (2026-10-21). Amended on 2026-10-27, after the owner's decisions on the rule terms review: point 5 citation, and Review for a party section without an LEI. Amended on 2026-10-29: the LEI of a person other than the parties counts toward neither Review condition of `COMMON.LEI_CONSISTENCY`. Amended on 2026-11-02, after an audit, its review and a second verification: in a section that reads LEIs, every LEI-like code that is not LEI-shaped sends `COMMON.LEI_CHECK_DIGITS` to Review, wherever it stands, so a malformed LEI next to a valid one no longer passes in the shapes listed below. The amendment first read only the code that a label introduced; the verification found list, bullet and line-wrap shapes that this reading missed, and a quadratic path, so the reading was replaced by one that read every LEI-like code in a section that reads LEIs. A third verification found that text the loaders leave out of every section (DOCX paragraphs in capitals, Word list items and table cells, PDF lines read as headings, XHTML markup outside the selected blocks, text under a Markdown sub-heading), sections that name no LEI, and codes of 16, 17, 23 or 24 characters, glued to their label, split by dashes or written with look-alike characters still passed, so a draft that reads LEIs now reads them in all its text, as described here.

## Context

White papers identify their parties by Legal Entity Identifier. The repo's study maps the LEI to Annex I, Part A (`ANNEX_I_PART_A_05_LEI_OR_IDENTIFIER` in `batch.py`). A mistyped LEI is a common, mechanical error that a deterministic check can catch. WhitePaperXBRL checks LEI check digits and optionally asks GLEIF, but treats a failed lookup as valid (Observed in its docs); that fails open. EUR-Lex was unreachable, so no new citation could be verified.

## Options

1. One rule, check digits only.
2. Two rules: check digits, and consistency between the party sections and the rest of the draft.
3. Option 2 plus a GLEIF registry lookup.

## Decision

Option 2, offline.

- **`COMMON.LEI_CHECK_DIGITS`** (MAJOR) reads the text of every section and, for a document file, the whole text of the file (`lei.py`):
  - **LEI-shaped codes.** A run of 20 characters, 18 upper-case ASCII letters or digits and then two digits, that is not part of a longer run of ASCII capitals and digits. Each has its check digits checked (`lei.find_leis`).
  - **Texts that read LEIs** (`lei.reads_leis`): the party sections (`issuer`, `offeror`, `trading_platform_operator`), and any text that names an LEI label or holds an LEI-shaped code with a letter. The label is LEI or LEIs as a word ("LEI-Nr.", "LEI code"), legal entity identifier(s) or legal entity ID, or Rechtsträgerkennung(en) (also Rechtstraegerkennung, and with the umlaut decomposed into "a" and U+0308), in any case. Any spaces, hyphens, dashes or line ends may stand between the words of the long labels, and a hyphen, a dash, a soft hyphen or a line end (with or without a hyphen) between any two of their letters, as a PDF or a word processor breaks a word ("Rechtsträger-\nkennung").
  - **A draft that reads LEIs reads them in all its text** (`lei.draft_reads_leis`): once it has a party section, or one of its sections or the text of its file reads LEIs, every section is read as a text that reads LEIs, and so is the text of a PDF, DOCX, Markdown, XHTML or HTML file outside its sections. The document loaders keep that text under the reserved metadata key `document_text`, which a JSON draft cannot set: for a PDF every extracted line, headings and running headers included; for a DOCX every paragraph of the body, of its tables and text boxes, and of the headers and footers each section defines, tracked insertions included; for Markdown the file as written; for XHTML and HTML every text outside the head, scripts, styles and templates, a line per block element and `<br>` (table cells, definition lists, spans, sections, headings and hidden iXBRL facts included), and for a saved iXBRL viewer page that of the markup it packs. So a code in a heading, in a DOCX paragraph that the loader takes for a heading because it has no lower-case letter, in a Word list item, in a table cell, on a PDF line that the loader reads as a heading or that drops out of every section, under a Markdown sub-heading, or in a section that is not a party section and names no LEI, is read. A code of the file text that no section holds (`lei.codes_outside_sections`) is named "outside the section text (in a heading, a table, a header or footer, or text in no section)". Only an LEI-shaped code in a section that reads LEIs on its own counts as found (below): one elsewhere adds an issue when its check digits fail, and never lets a draft without such a code pass.
  - **LEI-like codes** (`lei.lei_like_codes`). In a text that is read, every LEI-like code counts, wherever it stands. The text is split into groups, the runs of letters and digits of any script with any combining marks among them, so a look-alike (a Cyrillic "Ѕ", a full-width digit, an "S" with a combining accent) stays inside the code it stands in. An LEI-like code is:
    - one group of 16 to 24 characters that holds a digit or is in ASCII capitals, or one of 25 to 28 characters that starts with "LEI" in any case and holds a digit (a code glued to its label, "LEI9999SYNTH07000ZZQ02637"); or
    - groups joined by one to three spaces (no-break and thin spaces included), invisible characters (a zero-width space, non-joiner, joiner, word joiner or byte-order mark), hyphens or dashes (hyphen-minus, soft hyphen, hyphen, non-breaking hyphen, figure dash, en dash, em dash, horizontal bar, minus sign, small and full-width hyphen-minus) or line ends, with at most one hyphen or dash and one line end in each gap, that together hold at least 16 characters and a digit, or whose groups all have the same length ("XXXX XXXX XXXX XXXX XXXX"). A group of 16 or more characters, and "LEI" or "LEIs" in any case, do not join. A group of letters only that holds a lower-case letter or a letter outside ASCII is a word, and joins only beside a group of the same length that holds a digit, as in a code in lower case split into groups ("9999 synt h000 0zzq 0263").

    One that is not LEI-shaped as written is malformed (`lei.malformed_leis`): it has 16 to 19 or 21 to 24 characters, is in lower case, has a letter where a check digit belongs or a character outside ASCII, is glued to a leading "LEI", or is split into groups. The issue quotes it as written, with each run of spaces, invisible characters or line ends as one space, cut after 40 characters, so neighbouring groups that joined it ("CODE 9999 SYNT H000 0ZZQ 0263 HRB 12345") are quoted with it.
  - **Where this departs from the reading recommended by the verification** (every case-insensitive run of 18 to 22 letters and digits, or spaced groups that join to that length, in a section with a label), and why:
    - A run of letters only that holds a lower-case letter, or a letter outside ASCII, is a word, not a code. `examples/art-stablecoin.json` names "Aktiengesellschaft" (18 letters) in its labelled issuer section, so the recommended reading sends that example to Review; German legal prose is full of such words ("Handelsregisternummer", "aufsichtsrechtlichen"), and so are German headings in capitals ("RECHTSTRÄGERKENNUNG"). An LEI holds only ASCII letters and digits, and its last two characters are digits.
    - A word joins groups only beside a group of its length with a digit. If every word joined, prose such as "with a fictional registered seat and business address at Example Street 22" in the labelled offeror section of `examples/other-crypto-asset.json` would be one code and send that example to Review; if every word of up to four letters joined, "was founded in 2019 and has its seat in Berlin" would read "in 2019 and has its seat in" as a code of 21 characters.
    - A run of groups in capitals without a digit counts only if all its groups have the same length, so a heading in capitals ("INFORMATION ABOUT THE OFFEROR") is no code.
    - Groups count from 16 characters with no upper bound, so a spaced code with its neighbours ("LEI CODE 9999 SYNT …") is read; one group of more than 24 characters (28 for one with a digit after a glued "LEI"), such as a contract address or a hash, is not.
    - The whole text of a draft that reads LEIs is read, not only the sections that name an LEI, and not only the section text: a loader's heading detection and section boundaries are heuristics, and what they leave out must not hide a code.
  - **Limits: a code that is not seen**, so the rule can still pass while it is malformed or invalid:
    - Text the loaders do not extract: in a DOCX, footnotes, endnotes, comments, deleted text, field codes and text in charts, SmartArt or images; in a PDF, text that pypdf does not extract (images, scans, annotations, form fields); in XHTML or HTML, the head, scripts, styles and attribute values (alt or title text); in a JSON draft, everything outside `sections` (the title, other keys).
    - A code that is no LEI-like code: one group of fewer than 16 or more than 24 characters (28 for one with a digit after a glued "LEI"), that is a code that has lost or gained five or more characters; groups that together hold fewer than 16; one group of letters only with a lower-case letter or a letter outside ASCII; groups split by any other character (a full stop, a slash, a comma, an underscore), by more than three characters, or by two hyphens or dashes or two line ends (a blank line); a code split into groups where a word stands beside no group of its length with a digit; groups in ASCII capitals without a digit and of different lengths.
  - **False Reviews**, which fail safe: every LEI-like code in a draft that reads LEIs counts, wherever it stands, so an IBAN (with or without spaces, "DE00 0000 0000 0000 0000 00", "RO00SYNTH00000000000000"), a long number in groups, a placeholder such as "XXXXXXXXXXXXXXXXXXXX", a reference number of 16 to 24 letters and digits, an address or heading in capitals with a digit in it, a word of 16 to 24 ASCII capitals in any heading or text ("INTERESSENKONFLIKTE"), numbers in neighbouring table cells or lines that join, a valid LEI glued to "LEI" or split into groups, or a code that the file text and a section quote with different neighbours (named twice) gives Review; a 20-digit number anywhere in such a draft has its check digits checked.

  Statuses:
  - Missing: no section that reads LEIs on its own holds an LEI-shaped code (a purely numeric one counts only there) and no party section has text other than a placeholder (fail closed). A malformed code, or one with invalid check digits elsewhere, is named in the issues and does not change this status.
  - Review: any LEI-shaped code that is read fails ISO/IEC 7064 MOD 97-10, an LEI-like code is malformed, or no section that reads LEIs on its own holds an LEI-shaped code while a party section has text. Point 5 of each party Part allows another identifier required pursuant to applicable national law in place of the LEI, and the rule cannot recognise one.
  - Pass: a section that reads LEIs on its own holds an LEI-shaped code, every LEI-shaped code that is read has valid check digits and no LEI-like code is malformed.
- **`COMMON.LEI_CONSISTENCY`** (MAJOR) looks only at LEI-shaped codes with valid check digits, so a single typo, or a malformed code, is reported once, by `COMMON.LEI_CHECK_DIGITS`; a draft with a malformed LEI next to a valid one can pass this rule by design. Statuses:
  - Missing: no party section (`issuer`, `offeror`, `trading_platform_operator`) has text other than a placeholder.
  - Review: a party section has text but none has a valid LEI; a valid LEI outside the party sections appears in none of them; or `issuer` names more than one LEI.
  - Neither of the last two counts an LEI that the draft gives for a person other than the parties, which the template of Implementing Regulation (EU) 2024/2984 asks for: the crypto-asset service provider in charge of the placing (Table 2 field E.31, Table 3 C.22), a custodian of the reserve assets (Table 3 G.8), and a person other than the issuer who offers the token, seeks its admission to trading or draws up the white paper (Table 3 AA.1 and AA.3, Table 4 A.27). The field label or the sentence that holds the code must name the role before it (`lei.other_person_leis`).
  - Pass: otherwise.
- **Citation.** `Anhang I Teil A Nr. 5, Teil B Nr. 5, Teil C Nr. 5, Anhang II Teil A Nr. 5, Anhang III Teil A Nr. 5 MiCAR`, checked against the Official Journal on 2026-10-27. Point 5 of each party Part names the LEI or another identifier required pursuant to applicable national law, and Art. 2(1)(b) and (c) of Implementing Regulation (EU) 2024/2984 ask for the LEI where available. Releases 1.2.0 and 1.2.1 cite Part A of each Annex without a point, although Annex I Part A covers the offeror, and report Missing where the amended rules report Review. The amendment reached `main` on 2026-10-29, after 1.2.1.
- **Anchoring.** Both rules anchor to the `issuer` section for line mapping, the SARIF log and the review table. The playground names "every section" in its place and offers no "Inspect section" button for them (`ALL_SECTION_RULES` in `docs/playground/model.mjs`).
- **CI outputs.** Issue text quotes the LEI, so both rules are in `DRAFT_ECHO_RULES` and the SARIF log uses the fixed sentence instead; the job summary and annotations print no issue text.
- **Network.** No registry lookup: a pass means the characters are consistent, not that the LEI exists or belongs to the named entity.

## Consequences

- Each regime gains two rules, and every existing report gains two findings. The three full synthetic examples carry a fictional LEI with computed check digits and pass both rules; `examples/incomplete.json` has none and shows both as Review, because its issuer section has text.
- Rule IDs are new; no existing ID, status, severity or exit code changes. `--strict` is unaffected, because neither rule is a BLOCKER.
- The 2026-11-02 amendment changes no rule ID, severity or exit code and adds no status: a draft that gives a malformed LEI-like code anywhere in its text, or an LEI-shaped code with invalid check digits outside a section that reads LEIs on its own, next to a valid LEI, moves from Pass to Review on `COMMON.LEI_CHECK_DIGITS`, and a 20-digit number anywhere in a draft that reads LEIs has its check digits checked; the false Reviews above can move a draft from Pass to Review too. `COMMON.LEI_CONSISTENCY` still reads the sections only. The seven drafts in `examples/` give the same `--json` reports as before.
- The reading is one pass: the text is split into groups once, each group is classified once, each gap between two groups is looked at once and only if it is at most three characters long, only the groups that can be part of a code are looked at again, and the label search reads each run of spaces or line ends once. Its time grows linearly with the length of the text; in the tests, 200 KB of text, including a label followed by 200 000 line ends, is read in well under the 2 s bound. A document file's text is read once more besides its sections, so a file is read about twice. The result is kept for the last 64 texts read, so the two rules do not repeat it for the same text. The reading of 1 MB of text took about 0.25 s here. On 1 MB drafts (a Markdown or JSON offeror section of "LEI 1 " repeated, and 1 MB of Markdown prose) the whole CLI run took 1.2 to 1.5 s here, against 1.3 to 1.7 s on `main`, since the draft language, which every rule asks for, is now counted once per draft instead of once per rule; a test bounds both LEI rules on a 1 MB Markdown draft at 5 s.

## Non-negotiables check

- Fails closed when there is no LEI. In a draft that reads LEIs, an LEI-like code anywhere in the text the linter reads that is not an LEI with valid check digits never lets `COMMON.LEI_CHECK_DIGITS` pass, and a draft that reads no LEIs has no LEI to pass on. What the rule cannot see is listed under the limits above: text the loaders do not extract, and a malformed code that is no LEI-like code (such as one that has lost five characters, or one split by full stops). Such a code can pass, so the rule meets "a malformed or invalid LEI never ends in Pass" only for LEI-like codes in the text it reads. `COMMON.LEI_CONSISTENCY` leaves malformed codes to `COMMON.LEI_CHECK_DIGITS` by design.
- Deterministic, with no model and no network.
- Test LEIs are synthetic with computed check digits; no real identifier appears in the repo.
- The point 5 pinpoint was added on 2026-10-27 after the Official Journal check.
- Severity: MAJOR for both rules, confirmed by the owner on 2026-10-22.
- Owner decision of 2026-10-27: a party section without an LEI goes to Review, not Missing.
