# 0007. LEI check-digit and consistency rules

Status: Accepted (2026-10-21). Amended on 2026-10-27, after the owner's decisions on the rule terms review: point 5 citation, and Review for a party section without an LEI. Amended on 2026-10-29: the LEI of a person other than the parties counts toward neither Review condition of `COMMON.LEI_CONSISTENCY`. Amended on 2026-11-02, after an audit, its review and a second verification: in a section that reads LEIs, every LEI-like code that is not LEI-shaped sends `COMMON.LEI_CHECK_DIGITS` to Review, wherever it stands, so a malformed LEI next to a valid one no longer passes in the shapes listed below. The amendment first read only the code that a label introduced; the verification found list, bullet and line-wrap shapes that this reading missed, and a quadratic path, so the reading was replaced by one that read every LEI-like code in a section that reads LEIs. A third verification found that text the loaders leave out of every section (DOCX paragraphs in capitals, Word list items and table cells, PDF lines read as headings, XHTML markup outside the selected blocks, text under a Markdown sub-heading), sections that name no LEI, and codes of 16, 17, 23 or 24 characters, glued to their label, split by dashes or written with look-alike characters still passed, so a draft that reads LEIs now reads them in all its text. A fourth verification found that a character reference or markup inside a code of a Markdown draft, which the loader keeps as written, a code that a PDF table cell wraps with the next cell's words between its two pieces, format characters other than the five zero-width ones (left-to-right and right-to-left marks, bidirectional isolates, invisible operators) and some separators inside a code, a JSON section given as a list or an object, and a code glued to a word still passed, so each text is now also read as a renderer shows it, every format character and dash counts by its Unicode category, two pieces of a wrapped code are read as one, a JSON list or object is read as its text, and a word glued to a code no longer hides it, as described here. A fifth verification (2026-11-03) found that XHTML CDATA sections, entities a document declares in its own DTD and hidden text were not among the limits below, that a party table with its LEI label only in a header row was a realistic case of one, and that the timings were stated as if they were bounds; the limits now name them, and the timings are measurements. A sixth verification (2026-11-03) found that the CHANGELOG named the DTD-entity and CSS limits for XHTML only, while HTML files share them, as this ADR says; it changed no rule. A seventh verification (2026-11-03), of the merged changes, and its follow-up found that text a DOCX has moved away under tracked changes, PDF text drawn invisibly or in the colour of the page, and XHTML or HTML text hidden by the `hidden` attribute or `visibility:hidden` are read as if shown, which the limits did not say, and that the list reading that the changes after the fifth and sixth verifications added to regime inference took quadratic time on long lists; that list reading was backed out, the limits now name these texts, and no LEI rule changed.

## Context

White papers identify their parties by Legal Entity Identifier. The repo's study maps the LEI to Annex I, Part A (`ANNEX_I_PART_A_05_LEI_OR_IDENTIFIER` in `batch.py`). A mistyped LEI is a common, mechanical error that a deterministic check can catch. WhitePaperXBRL checks LEI check digits and optionally asks GLEIF, but treats a failed lookup as valid (Observed in its docs); that fails open. EUR-Lex was unreachable, so no new citation could be verified.

## Options

1. One rule, check digits only.
2. Two rules: check digits, and consistency between the party sections and the rest of the draft.
3. Option 2 plus a GLEIF registry lookup.

## Decision

Option 2, offline.

- **`COMMON.LEI_CHECK_DIGITS`** (MAJOR) reads the text of every section and, for a document file, the whole text of the file (`lei.py`):
  - **LEI-shaped codes.** A run of 20 characters, 18 upper-case ASCII letters or digits and then two digits, that is not part of a longer run of ASCII capitals and digits. Each has its check digits checked (`lei.find_leis`).
  - **Texts that read LEIs** (`lei.reads_leis`): the party sections (`issuer`, `offeror`, `trading_platform_operator`), and any text that names an LEI label or holds an LEI-shaped code with a letter, as written or as shown (below). The label is LEI or LEIs as a word ("LEI-Nr.", "LEI code"), legal entity identifier(s) or legal entity ID, or Rechtsträgerkennung(en) (also Rechtstraegerkennung, and with the umlaut decomposed into "a" and U+0308), in any case. Any spaces, hyphens, dashes or line ends may stand between the words of the long labels, and a hyphen, a dash, a soft hyphen or a line end (with or without a hyphen) between any two of their letters, as a PDF or a word processor breaks a word ("Rechtsträger-\nkennung").
  - **A draft that reads LEIs reads them in all its text** (`lei.draft_reads_leis`): once it has a party section, or one of its sections or the text of its file reads LEIs, every section is read as a text that reads LEIs, and so is the text of a PDF, DOCX, Markdown, XHTML or HTML file outside its sections. The document loaders keep that text under the reserved metadata key `document_text`, which a JSON draft cannot set: for a PDF every extracted line, headings, running headers and text drawn invisibly included; for a DOCX every paragraph of the body, of its tables and text boxes, and of the headers and footers each section defines, tracked insertions, text moved away under tracked changes (`w:moveFrom`) and any `w:t` inside a tracked deletion included; for Markdown the file as written (read as shown too, below); for XHTML and HTML every text that lxml's HTML parser keeps outside the head, scripts, styles and templates, a line per block element and `<br>` (table cells, definition lists, spans, sections, headings and hidden iXBRL facts included), and for a saved iXBRL viewer page that of the markup it packs. That parser drops a CDATA section and does not expand an entity that a document declares in its own DTD (see the limits). Hidden text is read as if it were shown: a DOCX run marked hidden (`w:vanish`), text a DOCX has moved away under tracked changes and any `w:t` inside a tracked deletion, PDF text that is drawn but cannot be seen on the page (see the limits), and XHTML or HTML text that CSS or the `hidden` attribute hides (`display:none`, `visibility:hidden`, `hidden`). So a code in a heading, in a DOCX paragraph that the loader takes for a heading because it has no lower-case letter, in a Word list item, in a table cell, on a PDF line that the loader reads as a heading or that drops out of every section, under a Markdown sub-heading, or in a section that is not a party section and names no LEI, is read. A code of the file text that no section holds (`lei.codes_outside_sections`) is named "outside the section text (in a heading, a table, a header or footer, or text in no section)". Only an LEI-shaped code as written in a section that reads LEIs on its own counts as found (below): one elsewhere adds an issue when its check digits fail, and never lets a draft without such a code pass.
  - **Each text is read as written and as shown** (`lei._shown`). Where markup or a character reference changes a text that is read (a section, or the text of the file), it is read a second time as a Markdown or HTML renderer shows it: HTML comments (from `<!--` to the next `-->`) and tags removed, a block tag (`p`, `div`, `li`, `td`, `tr`, `h1` to `h6` and the like) and `<br>` shown as a line end; character references (`&nbsp;`, `&#160;`, `&thinsp;`, `&ndash;`, `&shy;`, `&#8203;`) replaced by the characters they name; every run of asterisks, backticks or tildes, every bracket, every link target (`](…)`, `][…]`) and every backslash before punctuation or a line end removed; and every run of underscores at the edge of a word removed, while one inside a word ("snake_case") stays. This removes more than a CommonMark renderer does (an asterisk that is no emphasis, a reference inside a code span); since the text is read as written too, removing more only adds codes. Everything below applies to each reading. A malformed code of the shown reading is named in its section and quoted as shown ("9999 SYNT H000 0ZZQ 026" for `9999&nbsp;SYNT&nbsp;…`); an LEI-shaped code of either reading has its check digits checked. Only an LEI-shaped code as written counts as found (below), so a valid LEI that markup splits as written ("9999SYNTH**0000ZZQ0263**") adds no issue and does not count as found either.
  - **LEI-like codes** (`lei.lei_like_codes`, `lei._codes`). In a text that is read, every LEI-like code counts, wherever it stands. The text is split into groups, the runs of letters and digits of any script with any marks of the Basic Multilingual Plane among them (Unicode category M: combining accents, variation selectors such as U+FE0F), so a look-alike (a Cyrillic "Ѕ", a full-width digit, an "S" with a combining accent) stays inside the code it stands in. The character classes come from the Unicode database of the Python that runs the linter. An LEI-like code is:
    - one group of 16 to 24 characters that holds a digit or is in ASCII capitals; or a longer one that holds a digit and either starts with "LEI" in any case and has at most 28 characters (a code glued to its label, "LEI9999SYNTH07000ZZQ02637"), or leaves 16 to 24 characters with a digit once a word glued to it is taken away: its leading letters, its leading letters up to the last lower-case one ("KennungSYNTH…"), its trailing letters, or both ("Kennung9999SYNTH0000ZZQ026", "Code9999SYNTH07000ZZQ0263", "9999SYNTH0000ZZQ0263Kennung");
    - groups joined by any number of invisible characters and up to three spaces (no-break and thin spaces included), hyphens or dashes or line ends, with at most one hyphen or dash and one line end in each gap (so invisible characters alone join two groups too, as a left-to-right mark between "9999SYNTH" and "0000ZZQ0263" does), that together hold at least 16 characters and a digit, or whose groups all have the same length ("XXXX XXXX XXXX XXXX XXXX"). Invisible characters are every format character (Unicode category Cf: zero-width space, non-joiner and joiner, word joiner, left-to-right and right-to-left marks, bidirectional embeddings, overrides and isolates, invisible operators, the soft hyphen, the Mongolian vowel separator, the Arabic letter mark, the byte-order mark), every control character other than whitespace, and every mark outside the Basic Multilingual Plane. Hyphens and dashes are every dash of Unicode category Pd (hyphen-minus, hyphen, non-breaking hyphen, figure dash, en and em dashes, horizontal bar, two-em dash, small em dash, small and full-width hyphen-minus, and the other dashes), the minus sign, the hyphen bullet and the middle dots (U+00B7, U+2027, U+30FB and U+FF65). A group of 16 or more characters, and "LEI" or "LEIs" in any case, do not join. A group of letters only that holds a lower-case letter or a letter outside ASCII is a word, and joins only beside a group of the same length that holds a digit, as in a code in lower case split into groups ("9999 synt h000 0zzq 0263"); or
    - two pieces of a code that a narrow table cell wraps onto the next line, with the words of the next cells between them, as pypdf extracts a table laid out line by line ("Offeror LEI 9999SYNTH0000 Synthetic Offeror GmbH" / "ZZQ026 Frankfurt am Main"): a piece is one group of fewer than 16 characters that holds a letter and a digit, and a piece on a line that names an LEI label, or on the line before one, makes a code with the longest piece on the next line if the two hold at least 16 characters together.

    One that is not LEI-shaped as written is malformed (`lei.malformed_leis`): it has 16 to 19 or 21 to 24 characters, is in lower case, has a letter where a check digit belongs or a character outside ASCII, is glued to a leading "LEI" or to a word, is split into groups, or is two pieces of a wrapped code. The issue quotes it as its reading gives it, with each run of spaces, invisible characters or line ends as one space, cut after 40 characters, so neighbouring groups that joined it ("CODE 9999 SYNT H000 0ZZQ 0263 HRB 12345") are quoted with it; two pieces are quoted with an ellipsis between them ("9999SYNTH0000 … ZZQ026").
  - **Where this departs from the reading recommended by the verification** (every case-insensitive run of 18 to 22 letters and digits, or spaced groups that join to that length, in a section with a label), and why:
    - A run of letters only that holds a lower-case letter, or a letter outside ASCII, is a word, not a code. `examples/art-stablecoin.json` names "Aktiengesellschaft" (18 letters) in its labelled issuer section, so the recommended reading sends that example to Review; German legal prose is full of such words ("Handelsregisternummer", "aufsichtsrechtlichen"), and so are German headings in capitals ("RECHTSTRÄGERKENNUNG"). An LEI holds only ASCII letters and digits, and its last two characters are digits.
    - A word joins groups only beside a group of its length with a digit. If every word joined, prose such as "with a fictional registered seat and business address at Example Street 22" in the labelled offeror section of `examples/other-crypto-asset.json` would be one code and send that example to Review; if every word of up to four letters joined, "was founded in 2019 and has its seat in Berlin" would read "in 2019 and has its seat in" as a code of 21 characters.
    - A run of groups in capitals without a digit counts only if all its groups have the same length, so a heading in capitals ("INFORMATION ABOUT THE OFFEROR") is no code.
    - Groups count from 16 characters with no upper bound, so a spaced code with its neighbours ("LEI CODE 9999 SYNT …") is read; one group of more than 24 characters (28 for one with a digit after a glued "LEI"), such as a contract address or a hash, is not.
    - The whole text of a draft that reads LEIs is read, not only the sections that name an LEI, and not only the section text: a loader's heading detection and section boundaries are heuristics, and what they leave out must not hide a code.
    - Two pieces of a wrapped code make one code only where each is one group with a letter and a digit and one of their two lines names an LEI label. Read with groups of digits or capitals only, with spaced groups or without the label, codes on consecutive lines that are no LEI give Review in a draft that reads LEIs: the DTI and the functionally fungible group DTI of the template (9 characters each), a VAT number over a register number, and in `examples/review-bundle/compliance-checklist.md`, which names the LEI rules in lines with "ISO/IEC 7064 MOD 97-10" and rule IDs in capitals, thirteen false codes that changed its `--json` report.
    - The shown reading is read besides the text as written, not in its place: text a renderer does not show (an HTML comment, a link target) may still hold a code, and the written reading keeps apart what removed markup glues together.
  - **Limits: a code that is not seen**, so the rule can still pass while it is malformed or invalid:
    - Text the loaders do not extract: in a DOCX, footnotes, endnotes, comments, deleted text as Word writes it (`w:delText`), field codes and text in charts, SmartArt or images; in a PDF, text that pypdf does not extract (images, scans, annotations, form fields); in XHTML or HTML, the head, scripts, styles and attribute values (alt or title text); in a JSON draft, everything outside `sections` (the title, other keys).
    - A code that is no LEI-like code: one group of fewer than 16 characters, or of more than 24 (28 for one with a digit after a glued "LEI") that no glued word explains, such as a code with digits glued to it ("…026312345") or a code that starts with letters glued to a word with no lower-case letter before a capital at the join ("kennungsynth…", "CODESYNTH…"); groups that together hold fewer than 16; one group of letters only with a lower-case letter or a letter outside ASCII; groups split by any other character (a full stop, a slash, a comma, an underscore that is shown, a bullet), by more than three characters other than invisible ones, or by two hyphens or dashes or two line ends (a blank line); a code split into groups where a word stands beside no group of its length with a digit ("9999 synt habc defg h012"); groups in ASCII capitals without a digit and of different lengths; a code that a table cell wraps where a piece holds no letter or no digit or is split into groups, where neither line names an LEI label, where the two pieces are not on consecutive lines, or where the code wraps over more than two lines.
    - Markup or a reference inside text that a renderer does not show (an HTML comment, a tag's attributes, a link target) is read as written only, and a renderer that shows markup otherwise than `lei._shown` reads it (for example a reference it does not know) may show a code that neither reading sees.
    - A mark outside the Basic Multilingual Plane right after the last character of an LEI-shaped code counts as an invisible character after the code, not as part of it, so that code is still LEI-shaped.
    - XHTML CDATA sections: lxml's HTML parser, which reads every XHTML and HTML file for the sections, the numbered fields and the document text, drops a CDATA section as it drops a comment. A code inside `<![CDATA[…]]>` is not read, and a code with part of it in one is read without that part (`LEI: 9999SYNTH<![CDATA[0000ZZQ026]]>` reads as "LEI: 9999SYNTH", which holds no LEI-like code), so the rule can pass.
    - Entities that an XHTML or HTML document declares in its own DTD (`<!DOCTYPE html [<!ENTITY offlei "…">]>`) are not expanded: the text keeps the reference (`LEI: &offlei;`), so a code given through one is not read.
    - Hidden text is read as if it were shown: a DOCX run marked hidden (`w:vanish`), text a DOCX has moved away under tracked changes (`w:moveFrom`) and any text (`w:t`) inside a tracked deletion (`w:del`); PDF text that is drawn but cannot be seen on the page, such as text drawn invisibly (text render mode 3, as in an OCR layer), in the colour of the page (white on white), in a 0.1 pt font, under a white filled rectangle or outside the clipping path (the PDF loader reads the text that pypdf extracts, and pypdf does not look at the render mode, the colour, the clipping path or what the page draws over the text); and XHTML or HTML text that CSS or the `hidden` attribute hides (`<span style="display:none">`, `visibility:hidden`, `hidden`). A hidden fragment can complete a code that the document shows malformed, so the code reads as LEI-shaped with valid check digits and the rule passes: "9999SYNTH0000ZZQ02" shown and "63" hidden reads as the valid "9999SYNTH0000ZZQ0263" while Word shows and prints 18 characters. The section text of a DOCX holds only the runs and hyperlinks that stand directly in a paragraph of the body (python-docx's `paragraph.text`), so it leaves out text moved away or inside a tracked deletion, and also text in a tracked insertion (`w:ins`), a content control (`w:sdt`), a field result (`w:fldSimple`), a smart tag (`w:smartTag`) or a text box. With such a fragment this happens where the code stands outside the section text, such as in a table cell, a header or footer, one of those containers, text in no section, or a paragraph the loader takes for a heading (a Heading style or an outline level, or a short label set entirely in bold or with no lower-case letter, as a plain or list paragraph that reads "LEI: 9999SYNTH0000ZZQ02" is). Where the code stands in a run or a hyperlink of another paragraph of a section, list items included, the section text keeps it malformed, and the rule goes to Review. That holds only in a section the draft's regime keeps: the loader drops the sections of the other regimes (an ART draft its `emt`, `crypto_asset` and `not_approved_statement` sections, an EMT draft its `art` and `crypto_asset` sections, any other draft its `art` and `emt` sections), so a code in a dropped section, as when an Annex I draft is read as an ART, stands outside the section text and the rule passes; with `--type other` the same draft goes to Review. The rule also passes where part of the code stands in one of those containers ("9999SYNTH0000" in a run, "ZZQ02" in a content control and "63" moved away), since the section text then holds no LEI-like code. Text that Word shows but the section text leaves out works the other way there: a valid code that a tracked insertion, a content control, a field result or a smart tag completes with four characters or fewer reads as malformed in the section text, and the rule goes to Review, which fails safe; with five or more, what stays in the section text is no LEI-like code, and the rule passes.
    - A PDF party table whose LEI label stands only in a header row ("Party Name LEI Seat") above the data row in which the code wraps inside its cell ("Offeror Synthetic Offeror GmbH 9999SYNTH0000 Frankfurt" / "ZZQ026 am Main"): only a piece on a line that names an LEI label, or on the line before one, pairs with the next line, so the two pieces are not read as one code and the rule can pass, also when another row of the table holds a valid LEI.
  - **False Reviews**, which fail safe: every LEI-like code in a draft that reads LEIs counts, wherever it stands, so an IBAN (with or without spaces, "DE00 0000 0000 0000 0000 00", "RO00SYNTH00000000000000"), a long number in groups, a placeholder such as "XXXXXXXXXXXXXXXXXXXX", a reference number of 16 to 24 letters and digits, an address or heading in capitals with a digit in it, a word of 16 to 24 ASCII capitals in any heading or text ("INTERESSENKONFLIKTE"), numbers in neighbouring table cells or lines that join (in an HTML table of a Markdown draft too, whose cells the shown reading puts on lines of their own), two groups with a letter and a digit on a line that names an LEI label and the next line that together hold 16 characters, a word with a digit of more than 24 characters that a glued word explains ("Kryptowertetransfer2024Verordnung"), a valid LEI glued to "LEI" or to a word or split into groups (also by markup, as written), or a code that the file text and a section quote with different neighbours (named twice) gives Review; a 20-digit number anywhere in such a draft has its check digits checked.

  Statuses:
  - Missing: no section that reads LEIs on its own holds an LEI-shaped code as written (a purely numeric one counts only there) and no party section has text other than a placeholder (fail closed). A malformed code, or one with invalid check digits elsewhere, is named in the issues and does not change this status.
  - Review: any LEI-shaped code that is read fails ISO/IEC 7064 MOD 97-10, an LEI-like code is malformed, or no section that reads LEIs on its own holds an LEI-shaped code as written while a party section has text. Point 5 of each party Part allows another identifier required pursuant to applicable national law in place of the LEI, and the rule cannot recognise one.
  - Pass: a section that reads LEIs on its own holds an LEI-shaped code as written, every LEI-shaped code that is read, as written or as shown, has valid check digits and no LEI-like code is malformed.
- **`COMMON.LEI_CONSISTENCY`** (MAJOR) looks only at LEI-shaped codes with valid check digits, so a single typo, or a malformed code, is reported once, by `COMMON.LEI_CHECK_DIGITS`; a draft with a malformed LEI next to a valid one can pass this rule by design. Statuses:
  - Missing: no party section (`issuer`, `offeror`, `trading_platform_operator`) has text other than a placeholder.
  - Review: a party section has text but none has a valid LEI; a valid LEI outside the party sections appears in none of them; or `issuer` names more than one LEI.
  - Neither of the last two counts an LEI that the draft gives for a person other than the parties, which the template of Implementing Regulation (EU) 2024/2984 asks for: the crypto-asset service provider in charge of the placing (Table 2 field E.31, Table 3 C.22), a custodian of the reserve assets (Table 3 G.8), and a person other than the issuer who offers the token, seeks its admission to trading or draws up the white paper (Table 3 AA.1 and AA.3, Table 4 A.27). The field label or the sentence that holds the code must name the role before it (`lei.other_person_leis`).
  - Pass: otherwise.
- **Citation.** `Anhang I Teil A Nr. 5, Teil B Nr. 5, Teil C Nr. 5, Anhang II Teil A Nr. 5, Anhang III Teil A Nr. 5 MiCAR`, checked against the Official Journal on 2026-10-27. Point 5 of each party Part names the LEI or another identifier required pursuant to applicable national law, and Art. 2(1)(b) and (c) of Implementing Regulation (EU) 2024/2984 ask for the LEI where available. Releases 1.2.0 and 1.2.1 cite Part A of each Annex without a point, although Annex I Part A covers the offeror, and report Missing where the amended rules report Review. The amendment reached `main` on 2026-10-29, after 1.2.1.
- **Anchoring.** Both rules anchor to the `issuer` section for line mapping, the SARIF log and the review table. The playground names "every section" in its place and offers no "Inspect section" button for them (`ALL_SECTION_RULES` in `docs/playground/model.mjs`).
- **CI outputs.** Issue text quotes the LEI, so both rules are in `DRAFT_ECHO_RULES` and the SARIF log uses the fixed sentence instead; the job summary and annotations print no issue text.
- **Network.** No registry lookup: a pass means the characters are consistent, not that the LEI exists or belongs to the named entity.

## Consequences

- Each regime gains two rules, and every existing report gains two findings. The three full synthetic examples carry a fictional LEI with computed check digits and pass both rules; `examples/incomplete.json` has none and shows both as Review, because its issuer section has text.
- Rule IDs are new; no existing ID, status, severity or exit code changes. `--strict` is unaffected, because neither rule is a BLOCKER.
- A JSON section given as a list or an object is read as its items or its "key: value" entries, one per line, nested ones too; before, the loader wrote Python's representation of it ("['…', '…']"), whose escapes turned a zero-width space or a line end into the letters `\u200b` or `\n` and so split a code or glued a letter to it. This changes the text every rule reads for such a section; a section given as a string is read as before.
- The 2026-11-02 amendment changes no rule ID, severity or exit code and adds no status: a draft that gives a malformed LEI-like code anywhere in its text, or an LEI-shaped code with invalid check digits outside a section that reads LEIs on its own, next to a valid LEI, moves from Pass to Review on `COMMON.LEI_CHECK_DIGITS`, and a 20-digit number anywhere in a draft that reads LEIs has its check digits checked; the false Reviews above can move a draft from Pass to Review too. `COMMON.LEI_CONSISTENCY` still reads the sections only. The seven drafts in `examples/` give the same `--json` reports as before.
- Each reading is one pass: the text is split into groups once, each group is classified once, each gap between two groups is looked at once (a gap of more than three characters only to drop its invisible characters), only the groups that can be part of a code are looked at again, the pieces of a wrapped code are paired line by line through the longest piece of the next line, and the label search reads each run of spaces or line ends once. The shown reading removes comments with one forward search per comment and the other markup with two regular expression passes. Its time grows linearly with the length of the text; in the tests, a label followed by 200 000 line ends is read in under the 1 s bound, and 200 KB of other text (labels and digits, groups, markup, table pieces, invisible characters, glued words among them) in under the 2 s bound. A text with markup is read twice, and a document file's text is read once more besides its sections, so a Markdown file with markup is read about four times. The result is kept for the last 64 texts read, so the two rules do not repeat it for the same text. The character classes are built once, on the first reading (about 20 ms here). The figures that follow are measurements, not bounds: single runs (the CLI the better of two) on a 4-core Linux container with Python 3.14 on 2026-11-03, with the changes made after the fifth verification; another machine, load or text can take longer. Reading 1 MB of one text (`malformed_leis` and `find_leis`) took 0.1 to 0.6 s for text without markup (labels and digits, groups and codes on one line or many, line ends, invisible characters), 0.5 to 0.6 s for text dense with markup ("LEI **A1** _b_ &nbsp; [x](#y) <b>z</b> " repeated, or unclosed tags), and 1.3 to 1.4 s for text dense with underscores ("_a" repeated), the slowest shape measured. The whole CLI run (`--type other --json`) on a draft whose offeror section holds 1 MB of text of one such shape ("LEI 1 ", spaced capitals and digits, markup, underscores, line ends) took 0.5 to 1.8 s for JSON (`main` 0.4 to 2.1 s), 0.3 to 1.9 s for Markdown without underscores (`main` 0.15 to 2.1 s) and 3.1 s with them (`main` 0.6 s), 2.2 s for a DOCX with 1 MB of text in 170 paragraphs ("LEI 1 " repeated; `main` 2.4 s) and 3.2 s with underscores (`main` 0.8 s), 1.1 s for a DOCX of 50 000 empty paragraphs and 2.5 s for one of 60 000 runs in one paragraph (`main` 0.9 and 2.5 s), and 0.9 to 1.2 s for an XHTML file of 0.9 to 1 MB whose offeror paragraph is a run of inline spans (`main` 1.1 to 7.9 s; the XHTML text join now reads only the end of the word before each span). The changes that followed the sixth verification changed regime inference only, and the list reading that the changes after the fifth and sixth verifications added to it was backed out after a seventh, so of them there remain that a run with `--type` no longer reads the text for the regime and that a sentence break in a long line is found in linear time; neither changes the LEI reading. On the same machine, the CLI run (`--type other --json`, the better of two, in two rounds) on six Markdown drafts of about 1 MB of these shapes ("LEI 1 ", spaced capitals and digits, markup, underscores, line ends, line ends with spaces) took between 0.05 s less and 0.15 s more than with the code these figures were taken on, and between 0.13 s less and 0.06 s more once main's changes to the first-page statement (#77) were merged as well; PDF drafts were not measured again. A test bounds both LEI rules on a 1 MB Markdown draft at 5 s.

## Non-negotiables check

- Fails closed when there is no LEI. In a draft that reads LEIs, an LEI-like code anywhere in the text the linter reads that is not an LEI with valid check digits never lets `COMMON.LEI_CHECK_DIGITS` pass, and a draft that reads no LEIs has no LEI to pass on. What the rule cannot see is listed under the limits above: text the loaders do not extract (XHTML CDATA sections and entities a document declares in its own DTD among it), a hidden fragment that completes a code the document shows malformed, and a malformed code that is no LEI-like code in either reading (such as one that has lost five characters, one split by full stops, or one that a table cell wraps on lines that name no LEI label, as in a PDF party table with its label only in the header row). Such a code can pass, so the rule meets "a malformed or invalid LEI never ends in Pass" only for LEI-like codes in the text it reads. `COMMON.LEI_CONSISTENCY` leaves malformed codes to `COMMON.LEI_CHECK_DIGITS` by design.
- Deterministic, with no model and no network.
- Test LEIs are synthetic with computed check digits; no real identifier appears in the repo.
- The point 5 pinpoint was added on 2026-10-27 after the Official Journal check.
- Severity: MAJOR for both rules, confirmed by the owner on 2026-10-22.
- Owner decision of 2026-10-27: a party section without an LEI goes to Review, not Missing.
