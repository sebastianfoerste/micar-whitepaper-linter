# 0009. Read the declared white-paper type before inferring it from the prose

Status: Accepted. Decided on 2026-11-10 in a Claude Code session on the owner's instruction to answer the open decisions ("finish everything as you recommend. Do deep research if required. Answer everything yourself."); the owner has not reviewed the detail below. Built on 2026-11-11 (`src/micar_linter/declared_type.py`).

## Context

Until this record the regime (the white-paper type) was decided so:

- A JSON draft states it in its `type` field (`other` where the field is absent), and `--type` does not change it.
- Any other format takes it from `--type` (single-file runs only), otherwise from English phrases in its text (`_regime_pieces`, `_negated` and the pseudo-negations in `whitepaper.py`; the limits are listed in `docs/SETUP.md` and `CHANGELOG.md`).
- An XHTML or HTML draft in the numbered-field layout of Implementing Regulation (EU) 2024/2984 is never read for phrases, because the template wording names every regime. Without `--type` the loader stops: "`<file>` uses the numbered fields of Implementing Regulation (EU) 2024/2984. State the regime explicitly: other, art or emt." (exit 1; a directory run counts the file in `failed_files`, see ADR 0008).

The phrase reading cannot tell a white paper that mentions asset-referenced tokens from one that concerns one. A published white paper for another crypto-asset (a PDF read locally on 2026-11-03, not part of this repository) loads as an ART on `main` at 361ebde and at ab29114, because its introduction names asset-referenced tokens; no negation rule can fix that.

The templates carry a mandatory coded field for the type: Table 2 (other crypto-assets) F.4 "Type of crypto-asset white paper", code OTHR; Table 3 (ART) B.7 "Type of crypto-asset white paper", code ARTW; Table 4 (EMT) B.4 "Type of white paper", code EMTW. Field numbers collide across the tables: B.7 is "Legal entity identifier" in Table 2 and "Website of the issuer" in Table 4, F.4 is "Token-related risks" in Table 3, and B.4 is "Registered address" in Table 2 and "Third-party roles" in Table 3. A field number alone therefore says nothing about the type.

### Provenance of the field names and codes

- English field names: `template_fields.py`, taken from the "Field" column of the Official Journal text (OJ L, 2024/2984, 3.12.2024), read on 2026-10-27.
- Codes and German field names ("Art des Kryptowerte-Whitepapers" for F.4 and B.7, "Art des Whitepapers" for B.4): `template_types.py`, added by #98 (merged into `main` as c8cfe0a). Its docstring records that they were read on 2026-11-04 from the English and German Official Journal text as the Publications Office Cellar serves it.
- The same codes and names stand in the mirror legalize-dev/legalize-eu, `eu/47/32024R2984.md` (rows F.4, B.7 and B.4; repository head 5c9e2f17, fetched 2026-11-10), and in field 1 of the Annex of Delegated Regulation (EU) 2025/421 in the same mirror (`eu/cf/32025R0421.md`, list of predefined values "‘ARTW’ ‘EMTW’ ‘OTHR’").
- Web evidence gathered on 2026-11-10 (third-party copies and search snippets only): two further English copies (a PDF that a corpus describes as the EUR-Lex OJ PDF, without a signature that would confirm it, and a EUR-Lex CONVEX XHTML copy) give the same numbers, names and codes; no amendment or corrigendum to either act was found, which is absence of evidence, not a check of the EUR-Lex record.
- Not re-read from the Official Journal in this session: eur-lex.europa.eu, publications.europa.eu, esma.europa.eu and data.europa.eu were blocked. This record changes no legal value: `declared_type.py` imports the numbers from item 1 of `classification_data.ITEMS`, the English names from `template_fields.FIELD_NAMES` and the German names and codes from `template_types.FIELD_TYPES`, and holds none of its own.

### How published white papers print the field

Thirteen published white papers read as files on 2026-11-10 (local only, never committed) print the field in these forms: the field number and name followed by the code alone (five), the code with a gloss in brackets, inside a sentence or in the lines below it (four; two of them PDFs that also wrap the name over two lines), the code twice with the content column of the template reprinted between (one), and the name of the type in words with no code at all (three). Three of the thirteen print the name of Table 4 ("Type of white paper") on the Table 2 field F.4. The linter's PDF loader extracts one of them, a PDF, with the field run into the next on one line ("F.4 Type of white paper OTHR F.5 The type of submission NEWT"). Every iXBRL file also tags the type as a hidden enumeration fact.

## Options

1. Keep `--type` and the phrase reading only.
2. Read the type field as text: a recognised field name with exactly one code that agrees with its table, and nothing else declares a type.
3. Option 2, and also the iXBRL enumeration fact (`mica:OtherTokenTypeOfWhitePaper` and the like) and the taxonomy entry point.
4. A wider text reading that also accepts a code with a gloss or in a sentence, or the type in words ("Other crypto-asset token white paper").

## Decision

Option 2, read as narrowly as is certainly right. Where in doubt, text is no declaration.

The regime is taken, in this order, from:

1. `--type` (a single-file run of a PDF, DOCX, Markdown, XHTML or HTML draft);
2. the `type` field of a JSON draft (as before, a JSON draft is not read for a type field, and `--type` does not change its type);
3. the type the draft declares in its type field (new);
4. the phrase reading, unchanged, for a draft that is not in the numbered-field layout. A numbered-field draft that declares no type still needs `--type`.

What declares a type (`read_declared_type`):

- A type field is a line of the draft's text (the loaders' `document_text`; for a numbered-field draft the same text, one cell or block per line) that starts with one of the four names above, in any letter case, after nothing but a field number ("F.4", "F.4:", "F.04", "B.7 -") and the marks of a Markdown heading, quotation, bulleted list (`-`, `+`, `*`, `•`), table, emphasis or code span; or whose line before holds a field number alone. Any of the four names counts on any field number, since published papers print the Table 4 name on F.4.
- Its answer is the rest of the line after the name and a colon or dash, or, where nothing follows the name, the next line that holds text. After a field number, the answer ends before the number of the next field of the same part ("F.5" after "F.4") on that line. The field must end after its answer: the next field starts on the answer's line, the line after the answer starts with a field number, or the text ends. Otherwise the answer may go on (a gloss on the next line, a heading or paragraph after the field), and the field declares nothing.
- A line whose answer is a page number, with or without dot leaders, or that the number of the next field follows with no answer between ("F.4 Type of white paper" / "F.5 The type of submission", as a list of the fields without page numbers prints it), is an entry of a table of contents and no type field.
- The draft declares a type where it holds at least one type field, every type field it holds answers exactly one of OTHR, ARTW and EMTW, written in capital letters, alone (quotation marks around it and one full stop after it are allowed, as `ITS.CODE_LISTS` allows them), every such code is the same, and every field number printed with it is the number of that code's table (F.4 with OTHR, B.7 with ARTW, B.4 with EMTW). A field with no number counts by its code.
- The whole text of the file and the text as a reader sees it (`shown_text`, for DOCX, PDF, XHTML and HTML) must give the same reading; otherwise the draft declares no type. Hidden text therefore never declares a type, and a hidden second type field voids a shown one. No loader reads a Markdown file as shown, so a Markdown file that holds raw HTML, an HTML comment or a fenced code block declares no type where it holds a type field (an autolink such as `<https://...>` is no HTML).
- In a numbered-field draft the answer of the declared table's type field, as `numbered_fields.field_answers` gives it to `ITS.CODE_LISTS`, must be exactly the code on each of its lines too (`confirm_numbered`), so the declaration and that rule read the same field.

What does not declare a type, with the reason the note gives: a code whose field goes on (the next line starts no other field); two different codes, in one answer or across type fields; a code under another field number than its table's type field (B.7 or F.5 with OTHR, F.4 with EMTW); a code in lower or mixed case; any other answer (a gloss, a sentence, a submission code, the name of the type in words, a code inside a longer word, a later field number than the next one on the line, the reprinted content column); hidden text; Markdown that can hide text; and a numbered field that the field-level reading splits otherwise. A name that does not start its line (prose such as "enter EMTW in the field Type of white paper"), a list number before the name ("4. Type of white paper"), and another field's name under a colliding number ("F.4 Token-related risks" / "OTHR") are no type field at all, and give no note.

Fail closed. The declaration chooses which rule set runs and nothing else: a draft that declares type T gets exactly the findings, sections and notes of the same draft with `--type T`, plus one note. It never makes a rule pass that the draft does not pass under `--type T`. Where the declaration and the phrase reading disagree, the draft is linted under the declared type and the note says so; the template field is the issuer's own statement of the type, which the phrase reading cannot override, and the note sends the reader to check it.

Notes (extraction notes, in English):

- Declared, no regime stated: "The draft declares its type in the type field of the template of Implementing Regulation (EU) 2024/2984 (F.4 of Table 2): OTHR, a white paper for crypto-assets other than asset-referenced tokens and e-money tokens. No regime was stated, so the checks ran under the declared type (other)." Where the phrase reading gives another regime (not read for a numbered-field draft): " The wording of the draft reads as a white paper for an asset-referenced token (art); check which regime applies."
- Declared, and `--type` states another regime: the first sentence, then " The regime was stated as art, and the checks ran under the stated regime. Check which regime applies." `--type` stays the override. Where `--type` states the declared regime, there is no note.
- A type field that declares nothing, no regime stated: "The draft holds the type field of the template of Implementing Regulation (EU) 2024/2984, but it declares no type: <reasons>. The regime was inferred from the wording of the draft instead." A numbered-field draft has no wording to infer from, so the loader stops as before, and the reason follows its message: "... State the regime explicitly: other, art or emt. The draft holds the type field ..., but it declares no type: <reasons>." With `--type`, a type field that declares nothing gives no note.

Not built, and why. Option 3: the iXBRL fact sits in `ix:hidden` inside the hidden `ix:header`, which the loaders skip, and the ART and EMT element and member names were seen only in one third-party taxonomy bundle, not in the ESMA package or a published filing; it can follow once the ESMA taxonomy is read. Option 4: three of thirteen published papers print no code, and the wordings around a code vary; reading them would accept text that is not certainly a declaration. Other languages than English and German: the French, Portuguese and Czech names were read in mirrors only, and French uses one name for all three tables.

## Consequences

- No new output key. The source of the regime shows only in the note above, which every output that lists the extraction notes carries: the text report of a single-file run ("Warnings"), `--json` (`warnings`), the audit log (`--audit-log`), `--review-table-output`, `--remediation-output`, `--coverage-output`, the review bundle (`--review-bundle-dir`: compliance checklist, coverage matrix, remediation checklist, review table and reviewer sign-off), `--workspace-output` and the playground. SARIF (`--sarif-output`), `--summary-output`, `--annotations-output`, the console table of `--coverage`, `--manifest-output`, the console output of a directory run and the directory batch pack (`--batch-output`, `whitepaper_type` per file) do not show it (checked on 2026-11-12 with a synthetic Markdown draft that declares OTHR); a file that a directory run cannot lint keeps its loader message, with the reason, in the pack's `warnings` (`lint-failed:`).
- A numbered-field draft that declares its type is linted without `--type`, also in a directory run, where it counted in `failed_files` before (ADR 0008). `examples/numbered-other-draft.xhtml` has no field F.4, so it still needs `--type` and its output is unchanged.
- `--json` of every file under `examples/`, with no flag and with `--type other`, `art` and `emt` (14 files, 56 runs; stdout, stderr and exit code: 168 outputs), is byte-identical to `main` at 361ebde and, after merging it, at ab29114.
- Regime corpora (the generated drafts of the earlier regime work, kept outside this repository, loaded without `--type`, run on 2026-11-12 against `main` at ab29114): 76,779 files (49,825 + 16,800 + 1,040 + 1,904 + 6,832 + 378 in six sets) give the same regime as on `main`, and none of them holds a type field, so none gets a note. The LEI fail-closed sweeps (15 probe scripts, and `COMMON.LEI_CHECK_DIGITS` over 3,394 files under no stated regime and each of the three: 13,576 rows) give the same output; one row, a 60-second time limit of the harness that fired inside the loader during the parallel run on `main`, was the same under both trees when run alone.
- On the twelve published white papers available locally as files (eleven from the web research of 2026-11-10, read as `.xhtml`, `.pdf`, `.md`, and `.mdx` copied to `.md`, and the PDF of 2026-11-03; none is in this repository), the declared type is read in four, each OTHR as the paper prints it (two numbered-field iXBRL XHTML files, each with a list of the fields without page numbers before the field, which needed `--type` on `main` and are now linted as other; one `.mdx` file read as Markdown, as other on `main` too; and the PDF that loads as an ART on `main`, which now loads as other with the note that its wording reads as an ART); none is read as another type. The other eight declare nothing and load as on `main`: four numbered-field XHTML files whose field holds a sentence, a data-type word ("enumeration") or the type in words still need `--type`, with the reason in the message; one `.mdx` file holds HTML (JSX components); one Markdown file prints a bare list number ("4.") before the name; two PDFs wrap the name of B.4 over two lines.
- The playground asks for the regime of every XHTML draft, so it always states one; a draft whose type field declares another type gets the second note.
- The reading goes once over the lines of the text. Measured on 2026-11-11: 0.04 to 0.08 s for 400 000 characters of type-field lines of several shapes, 0.4 to 0.9 s for 4 000 000 (ten times the time for ten times the text); the test bounds 400 000 characters to 3 s.
- Limits. A type field is read only where its name starts a line of the extracted text, so a field that a PDF extracts in the middle of a line, or whose name it wraps over two lines (as the linter's PDF loader extracts two published EMT papers, "B.4 Type of white" / "paper" / "EMTW"), declares nothing; nor does a bare list number before the name. The answer is one line, and the field must end after it: a code that stands after a page number or other text on the next line declares nothing, and nor does a field that the text of the next section follows without a field number, as in a draft that gives the type field alone under a heading. Only the four English and German names count. Markdown is read as written, so markup other than raw HTML, comments and code fences (an escaped character, an entity) makes the answer "other text". The phrase reading of a draft that declares no type is unchanged, with its limits.

## Non-negotiables check

- Fail closed: a draft that declares no type, or whose type field is unclear, hidden or contradicted, is handled exactly as before; a declared type gives exactly the findings of `--type` with that type, and a disagreement with `--type` or with the wording is reported.
- No model and no network in the checking path; the reading is a regular expression over the loaders' text, in linear time.
- Synthetic fixtures only (`tests/test_declared_type.py`); the published papers used for the research are not in the repository.
- Not legal advice: the note asks the reader to check which regime applies.
