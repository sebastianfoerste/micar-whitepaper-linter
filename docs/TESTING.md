# Testing & Verification: MiCAR Whitepaper Linter

The testing suite verifies rules logic, document parsers, and CLI options.

Develop with `make check` (ruff, pytest, CLI smoke, review bundle, playground and template checks).

The full `make check` gate also requires Node.js 22 or later for the browser's dependency-free JavaScript tests. Run `make playground-check` for those checks alone. The Python bridge tests compare browser JSON/text payloads with CLI output for all bundled examples, retain the review gates, and verify draft cleanup after failure.

The playground examples are generated from `examples/`. After changing a canonical example, run `make playground-samples`; the Python suite rejects stale bundled examples. The prebuilt Python wheel has a separate source-parity test. The sample reports in `reports/` and the CLI output in `docs/sample-review-bundle.md` are real CLI output in the default English citation style: after changing report text, a rule, `examples/art-stablecoin.json` or `examples/incomplete.json`, run `make sample-reports`; the Python suite rejects stale copies. No script regenerates the example output blocks in `README.md` and `docs/DETAILS.md`: after a report change, update them by hand; `tests/test_readme.py` rejects a block that is not the start of the real CLI output. The README screenshot is captured from the CLI: after changing report text, `examples/incomplete.json` or `scripts/render_demo.py`, run `make demo-image`, which needs headless Chrome or Chromium (`make demo-image CHROME=/path/to/chromium`), and commit `docs/demo.txt` and `docs/demo.png`.

For browser checks, serve `docs/` over HTTP and open `/playground/`. Exercise each example, search and status filters, section navigation, malformed JSON, edits during/after a run, import and export, and runtime failure/retry. Check both the two-column desktop view and the stacked mobile view. Use synthetic data only.

---

## Testing Tools

1. **Unit Tests**: Powered by `pytest` (configured in [pyproject.toml](../pyproject.toml)).
2. **Formatting & Linting**: Handled by `ruff`.

---

## How to Run Tests

### 0. Run The Local Proof Gate
Runs ruff, pytest, a JSON CLI smoke check against the ART example, and the review bundle, playground and template checks:
```bash
make check
```

### 1. Run Python Test Suite
Runs the complete pytest suite:
```bash
uv run --extra dev pytest
```

### 2. Run Formatting Checks
```bash
uv run --extra dev ruff check src tests scripts
```

## Key Test Areas
- **German Language Rules**: Validated in `tests/test_german.py`.
- **iXBRL XHTML Parsing**: Validated in `tests/test_ixbrl.py`.
- **Regime Rules**: Validated in `tests/test_rules.py` (verifies checks for Annex I, II, and III).
- **ART Reserve Floor**: Validated in `tests/test_reserve_rules.py` across draft characterisation combinations, malformed values, percentage formats, misleading contexts and the invariant that the rule never returns `PASS`.
- **Format Parsers**: Validated in `tests/test_markdown.py` and `tests/test_document.py` (DOCX, Markdown). `tests/test_heading_detection.py` builds DOCX files with python-docx and PDF files that pypdf parses, in plain, bold and larger type (14 pt bold headings, one or several pages, laid out with Td or T*), and Markdown and heading-layout XHTML drafts, and checks section keys and BLOCKER statuses: body text mentioning a section word opens no section; list items, wrapped lines and lead-ins stay in their section; a line rejected as a heading ends the section before it; a heading that wraps onto two lines in its heading font is one heading, while two headings a paragraph apart stay two, and so does a short heading one line spacing above the next heading or above a bold paragraph in a draft with no space between paragraphs; a short heading over a lower-case line in its font stays a heading; a heading font wins over a following lower-case list item; marked part titles of up to 20 words without the part letter are headings; the part titles, the plural Part F title and the numbered fields of the Implementing Regulation template are headings; a heading that names no section ends the section before it while a sub-heading does not, such as a smaller heading, a bold label under a bold heading, a heading numbered below the heading that opened the section ("12.1" under "12.") or one that names a single risk ("Market risk"); German headings that name the date of notification or the redemption ("Datum der Mitteilung", "Rücktausch") open their sections; a heading that names a risk and the redemption ("Redemption risk", "Rücktauschrisiko") stays with the risks, and a redemption heading below the rights heading, a redemption field of the template's Part D among them, keeps the rights section open; a cover title that names a section sets no heading level for the headings after it; summary table rows keep their answer, and the "Compliance statement" field opens the management statement; a running page header and a body-font line in a draft with a heading font open no section; heading text is not section body; in a DOCX or PDF the regime is read from headings and from text in no section (in a DOCX only from the runs and hyperlinks that stand directly in the paragraphs of its body, so not from a table, a header or footer, or text inside a tracked insertion or move, a content control, a smart tag or a simple field), in Markdown and XHTML only from section text (also from the text after the first-page statement in the line where it ends in Markdown, not the next line of its paragraph, and in the paragraph where it ends in XHTML and HTML), and not from a negated phrase such as "not an asset-referenced token" (a pseudo-negation such as "not limited to", "without limitation", "not only" or "not necessarily" governs no list item after it in any format, nor in a DOCX or PDF a line without a marker after a lead-in that ends in a colon, while it still negates a phrase in its own sentence, also one split over lines, and a negation beside it in its lead-in, also one before "but" in "including but not limited to", still negates), and a negation at the end of the paragraph or section before a heading does not reach the heading, while one in a DOCX or PDF paragraph reaches the next paragraph or line when that continues its sentence (it starts in lower case, or is a list item after a negated lead-in) and not when it starts a new sentence with a capital letter, a digit or a name with a capital letter, or follows a line shaped like a title; in a DOCX or PDF a negated lead-in governs the items of a dash, bullet or bracket list after it, and a sentence after the list that names the regime, or a numbered heading after it, still sets the regime, as does a line that reads as a heading, in the body font, in bold or in 14 pt, after a list of two or more items whose items before the last end in a semicolon and whose last item ends in a full stop, while the lead-in still governs the items of a list that is not closed so (items without a semicolon or with full stops, one item, a last item without a full stop) or that goes on (an inner list that a full stop closes, a lower-case item, a sentence, or a line that starts with "A" or "An", a digit, an outline number or a quotation mark or ends in a colon after the closing item, the items after a heading, a list after a new lead-in); the documented limits of the regime reading keep the results that the CHANGELOG and `docs/SETUP.md` state (among them those of the lead-in that decides whether a pseudo-negation is its only negation word: in a DOCX or PDF it stops at a line that starts a clause or after a line that ends in a sentence mark or colon, and in Markdown at a hard line wrap after one, it reaches past a line that ends in a semicolon, and a list nested under a lead-in with only pseudo-negations continues that lead-in), and a phrase that a line end splits inside one paragraph is found only in XHTML and HTML, with or without a space or line end beside the `<br>`; a long word, a long list and long lists that a full stop closes are read in linear time, a long Markdown list in little memory, and a regime that `--type` gives is not inferred; and DOCX styles that loop or are based on a numbering style load. `tests/test_document_loader.py` checks that study runs use the shape rule of `micar-lint` without font information.
- **LEI Rules**: Validated in `tests/test_lei.py`: check digits, malformed codes next to a valid one, codes that a loader leaves out of the sections, linear-time reading, and documented limits of the reading. Hidden text: the DOCX, PDF, XHTML and HTML drafts whose offeror code is shown malformed and completed by hidden text, in each place the loaders read (a body paragraph, a list item, a label paragraph, a table cell, a header, a tracked insertion, a content control, a field result, a smart tag, a text box, a code split between a run and a content control, a section the regime drops; a run hidden with `w:vanish` on it or in its styles, white, white on shading or a highlight that is white or has no fill, white by a theme colour, in a half-point font, scaled to 1 % width, moved away or inside a tracked deletion; a table style that hides, whitens or shrinks its table's text; PDF text in render mode 3 or 7, white set with `rg`, `g`, `k` or `sc`, in a named, ICC-based or calibrated colour space or as the stroke of render mode 1, in a font under 1 pt, squeezed by `Tz` or the text matrix, flattened by a slanting text matrix, in optional content that is off (by name, base state, membership policy, visibility expression, nested marked content, a form XObject) and in a form XObject; XHTML and HTML text that `display:none`, `visibility`, `content-visibility`, the `hidden` attribute, the browser's own style sheet, fallback content, a closed `<details>` or `<dialog>` or an SVG drawing hides, and `style` attributes whose invalid, later, `!important`, escaped or commented declarations CSS reads otherwise than a plain reading would), which go to Review; the same drafts with the completion shown, which pass (a DOCX completion in a tracked insertion goes to Review in a body paragraph, a list item or a section the regime drops, whose section text quotes the code malformed); and the hidden text that is still read as if shown (a PDF character under a white rectangle, clipped away, in a 1 pt font or white in a Lab colour space; HTML text that a style sheet, `opacity`, `font-size` or `color` hides), which passes. Also: how a DOCX is read as Word shows it (tracked changes, paragraph marks, table styles and the default table style, cell shading and nested tables, a nested cell's own white or nil shading, the `w:vanish` toggle, theme shades), that each XHTML reading keeps blocks apart, that a PDF number too large for a float in an operand this reading follows (a colour, `cm`, `Tf`, `Tr`, `sc` or `scn`, a form matrix, a marked-content name) does not stop it (one that pypdf itself cannot read, as for `Tz`, still stops the file, as on `main`), that a comment in a DOCX theme, a PDF page whose `/Parent` is no dictionary and nested PDF forms whose `/Matrix` does not hold six numbers do not stop the reading, that the graphics state is restored after a PDF form whose `/Matrix` does not hold six numbers or an XObject whose `/Subtype` is not `/Form`, so a colour or render mode its content sets does not show hidden text after it, that an array that membership dictionaries share inside their visibility expressions reads as it reads alone, also where the 10,000 reads run out inside it, that a hidden separator that takes up room on the page (DOCX white or under 1 pt, every kind of hidden PDF text) splits a valid code as the page does while one left out of the page does not, that one under 1 pt can split a malformed lower-case code so that it is not read (a documented limit), that a reading as shown that fails for any reason (the DOCX look, the PDF visitors, resources or lines, the XHTML walk) leaves the file read as without it, the issue that names a code only the shown text holds, that this text can only add issues and that a JSON draft cannot set it, and the time of both readings on large inputs, long `style` attributes, a long DOCX `w:basedOn` chain and PDF optional content named again and again among them (also membership dictionaries whose visibility expressions share an array inside them). These keep those cases in step with ADR 0007 and the rule page. A code in a DOCX section that the regime drops (given with `--type`, or inferred as an ART from a risk list after a pseudo-negation or a heading after a closed negated list) goes to Review when that section shows it malformed, with its last character moved away, deleted or nowhere, when a tracked insertion completes it (fail-safe), and when a hidden run (`w:vanish`) completes it, which only the reading as shown tells apart; shown valid, it passes.
- **Placeholders**: Validated in `tests/test_placeholders.py` ("TBD", "TBA", "[●]", "[...]", "[insert date]", "XX", "to be confirmed", "noch offen" and the other markers as a whole section, numbered field or part with "N/A" read as missing, and so does a section that still opens with the starter template's "REPLACE:" note; short real answers such as "TBC Freight Lines" do not).
- **Proof Contract**: `tests/test_proof_contract.py` checks that `contracts/micar-whitepaper-linter.proof.v1.json` carries the `micar-whitepaper-linter.proof.v1` schema identifier, names exactly the console scripts in `pyproject.toml` plus `action.yml`, gives `make check` as its verification command and that test as its `contractTest`, and that its output schema occurs in the source. Its other fields are not checked.
- **Reviewer Artifacts**: Validated in `tests/test_artifact_manifest.py`, `tests/test_remediation.py`, and CLI tests for manifest, remediation, audit-log, and write-failure behavior.
